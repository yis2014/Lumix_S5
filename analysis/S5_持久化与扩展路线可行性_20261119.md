# DC-S5 持久化与扩展路线可行性评估

更新时间：2026-11-19

## 结论

当前证据足以继续做 RAM-only 的观测和验证，尚不足以支持机身 body payload 密钥恢复或持久化免签固件。主核冷函数 detour 已经证明代码执行面存在，真正的机身更新验签入口、早期引导信任边界和持久化写入接口仍未得到实证。

## 证据分层

| 目标 | 当前判断 | 依据 |
|---|---|---|
| 恢复 body payload 密钥 | 低 | 静态搜索和已有 RAM 窗口没有得到经过已知明文验证的机身密钥，实际机身更新路径也没有命中可复核的 AES 调用 |
| 持久化跳过验签 | 很低 | 已确认的探针位于 RAM 和冷函数层，尚未进入 Reset 交接前、postboot 装载前或机身写 Flash 前的信任边界 |
| 官方启动后的扩展 | 中等 | Service USB 主核代码执行已实证，仍需确认系统是否存在合法的应用层、脚本层、菜单层或外设服务加载面 |
| RAM-only 研究载荷 | 高 | Service USB 读 RAM、半字写入和冷函数触发均已有真机记录 |

## 推荐研究链

1. **离线包一致性分析**

   以官方 V2.8 和 V2.9 为基线，完整解析容器目录、组件摘要、长度字段、版本字段、加密载荷边界和元数据公钥引用。所有结论先由离线校验器复核，再做真机只读观察。

2. **更新阶段只读观测**

   围绕已有的 `0x800003C4`、`0x868F9A0C` 和 `0x8F000100` 捕获区，记录状态码、分支目标、错误返回和装载地址。每轮只观察一个阶段，保留热重启前后的完整窗口。

3. **合法扩展面清单**

   检查官方启动完成后是否存在用户态服务、SD 卡资源加载、脚本解释器、USB 命令扩展、网络服务或菜单资源覆盖接口。优先采用设备已有的加载机制，验证范围限定为 RAM 和用户数据区。

4. **RAM-only 原型**

   先实现一个只读状态显示或日志捕获原型，证明启动后扩展的调用约定、任务上下文和资源边界。热重启后状态应自然消失，作为回滚基线。

5. **停止条件**

   若两轮独立只读观测仍无法确认机身更新验签入口，且系统没有可复核的官方扩展面，则把密钥恢复和持久化路线标记为未证实，继续维护离线解析器和 RAM-only 工具链。

## 当前不应作为成功标准的指标

- 版本头修改后能进入固件更新菜单
- 25% 阶段退出或重启次数变化
- 镜头更新路径的恒真返回
- 未经过已知明文验证的高熵 RAM 片段

这些现象可以作为阶段信号，不能单独证明机身验签已绕过或获得了可持久化执行权。

## 当前 RAM-only 基线

2026-11-19 的两次只读复读间隔约 0.5 秒，结果完全一致：

- `0x800003C4` 前四字节为 `d8 f0 9f e5`，符合基线。
- `0x868F9A0C` 前四字节为 `82 00 00 ea`，符合基线。
- `0x87086A00` 为重复的 `cd cc cc 3d` 浮点表前缀。
- `0x8F000100` 和 `0x8F000200` 的 magic 为零，两个计数器均为零。
- 原型记录 `write_operations=0`，本轮没有写 RAM 或执行载荷。
