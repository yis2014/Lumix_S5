## 3. 突破二：验签函数定位与返回约定

### 调用链（升级器 → 验签）

```
升级器主体 0x86867500 附近
  ├─ bl 0x868C72DE   ; 把密钥库指针 0x06F53764 写入升级上下文 +0x64
  ├─ bl 0x868C69EC   ; 设置工作缓冲
  └─ ... → ECDSA 包装函数 0x868C08C6
            └─ 核心 0x868CA60E   ; 求逆 s、u1=z·w、u2=r·w、u1G+u2Q、x mod n 与 r 比较
```

- 大数/ECC 运算区：`0x8643xxxx`（模乘等）、`0x868CDxxx–0x868CExxx`（点运算）
- AES S-box `0x86F50454`、逆 S-box `0x86F50554`；SHA-256 初始值 `0x868C34DC`
- 整个密码模块集中在 `0x868Bxxxx–0x868C7xxx`，与 LENS 升级解析器同区

### 结论

**验签包装函数 = 物理 `0x868C08C6`，返回 `0` = 签名有效，`1` = 无效。**

参数：`r0` = 公钥点（X‖Y 各 32B），`r1` = 32 字节摘要， `r2` = 签名（r‖s 各 32B）。

输入编码（由仿真矩阵确定，见 `verify_encoding_matrix.json`）：
- 摘要：**SHA-256 原始字节（大端），不要反转**
- 签名：**按升级文件 `0x220:0x260` 原样**
- 公钥：按固件中存储原样

被签消息：`file[0x2A0:0x142C]`（48 项目录），r/s 分别在 `file+0x220` / `file+0x240`。

### 仿真的三个坑（已在脚本中解决）

1. **双映射**：代码按物理地址执行（`blx 0x866Cxxxx`），只读数据按虚拟地址引用（`0x06xxxxxx`），因此同一镜像必须同时映射到 `0x06280000` 与 `0x86280000`。
2. **VFP 非法指令**：`__aeabi_memclr`（物理 `0x866C261C`，`dst=r0`、`n=r1`、填 0）在本固件里用 VFP 实现，unicorn 直接跑会 `UC_ERR_INSN_INVALID`。脚本用 Python 接管该函数。
3. **内存重叠**：暂存区不能放在 `0x07000000`（落在镜像映射内），现用 `SCRATCH=0x0B000000`、`STACK=0x0C000000`、返回哨兵 `0x09000000`。

## 8. 密钥链追踪进展（路线 1，同日）

### 已查清的 AES 使用方式

| 项目 | 结论 |
|---|---|
| 算法 | **AES-128**（密钥长度由 `movs r1,#0x80` 设置） |
| S-box / 逆 S-box | `0x86F50454` / `0x86F50554`（全转储仅此一份软件 AES） |
| 密钥扩展 | `0x868C044A`（读 key 字 → bswap → 写轮密钥表） |
| setkey 包装 | `0x868C0612`（加密）/ `0x868C06B8`（解密），参数 `(ctx, key, keybits)` |
| 上层密钥设置点 | `0x868C6B8E` 调 `0x868550D4` |
| **密钥来源** | **`r6 + 0x80`，其中 `r6 = [升级上下文 + 0x58]` = UPD 头部缓冲区** |
| IV 来源 | `[sp,#0x54] + 0x34`（升级上下文 `+0x34`） |
| 模式设置 | `0x868C6B80` 处 `r1=1` 调 `0x868550CC` |

### 已证伪

- **零密钥不成立**：V2.9 文件头 `0x80–0x90` 全为 0，但用 AES-128-CBC/ECB 零密钥解 `program` 分区（文件偏移 `0x17E00`）得到的是随机字节，与 RAM 明文 `70 f0 9f e5 ...`（ARM `ldr pc,[pc,#0x70]`）完全不符。
- 因此"密钥=文件头 `+0x80`"这条路径**不是 V2.9 机身载荷的解密路径**（头部该字段 `+0x2c = 0x300`，与代码中 `cmp r0,#2` 的加密分支不匹配）。该路径更可能属于**镜头（LENS）升级包**——镜头包自带密钥在头部，且 LENS-UPDATE 字符串就在同一模块。

### 下一步精确动作

1. 区分机身载荷解密与镜头包解密：机身 `program` 分区的实际解密大概率发生在 **postboot/loader 的升级上下文**（主核 `program` 只负责解析与验签），需在转储的 postboot 区找硬件 AES 引擎寄存器操作或第二套加密封装；
2. 检查升级数据流的**虚函数表**（`0x868C6BB2` / `0x868C6BBE` 的 `blx r1` / `blx r3`），这是读取-解密的间接调用点，静态直接调用扫描覆盖不到；
3. 若确认使用硬件 AES（Venus 引擎），则密钥可能来自 OTP/EEPROM 派生，需要转向运行期上下文抓取，而非静态字节搜索。

## 13. AES 密钥深挖（2026-11-18 主线）

### 新定位到的真实加解密对象
软件 AES 是**标准 Rijndael**（密钥扩展 0x868c044a 含 Nk>6 分支与 Rcon），不是减轮实现。
通用 AES-CTR 上下文对象（key 存 `ctx+0x170`，位数存 `ctx+0x10`，轮密钥 `ctx+0x14`）：
- 构造函数 0x868551ba（默认 128 位）；设钥 0x868550ec（memcpy 到 ctx+0x170）
- 加密设钥包装 0x868c0612（唯一调用 0x86855128）、解密 0x868c06b8（唯一调用 0x86855266）
- 设钥调用点：0x868ae420、0x868ae5f0、0x868c6b7c、0x868c6ea0

### 升级流密钥位置
0x868c6e60 起：按 `[升级上下文+0x34]` 的值分派加密模式（2 / 3），
`r7 = 上下文 + 0x34` 同时被用作 AES-CTR 的**密钥指针**，`[sb+0x69]` 为启用标志。
→ 载荷密钥是**运行期写入升级上下文的**，不是简单等于 UPD 头某字段。

### 已证伪（避免重复劳动）
- 0x868ae41c 常量池指向 0x86f5037c 的 16 字节是 `0123456789abcdef`×2 = **AES 自测占位密钥**，不是载荷密钥。
- UPD 头前 0x400 字节全部 16 字节窗口作 key × {CTR,CBC} × IV=0：0 命中。
- AES 表区 0x86f50000-0x86f50600 全部窗口 × IV{0, hdr+0x34, hdr+0x44} × {CTR,CBC} 共 8514 组：0 命中。
- V2.9 头 `0x34:0x44` = `03000000 00020000 00ec6005 c0aa738e`（含模式=3 与 8 字节随机量，疑似 IV/盐）。

### 下一步
用现有 Unicorn 框架**仿真升级流解密设置段（0x868c6e60 所在函数）**，
输入真实 V2.9 头，直接读出写入 `ctx+0x34` 的 16 字节密钥与 IV；
若密钥来自更上游的派生函数（EEPROM/主密钥），沿仿真中的内存读取继续回溯。

## 14. 密钥恢复：穷举与内存取证结论（2026-11-18）

### 最终机制
UPD 解析：`[UPD头+0x34]==2` 的分区走 AES-CTR，**key=分区对象+0x34（运行期填充）**，IV=UPD头+0x80（V2.9 全零）。
另有 `[对象+0xC]` 控制的**按 32 位字取反**混淆（0x868c6ac4 的 mvns 循环）。

### 全部阴性结果（不要再重复）
- UPD 头+分区表 0x2000 全部窗口 × CBC(第二块)/CTR × 取反变体：13666 组 0 命中
- 哈希派生（SHA256/SHA1/MD5 × 元数据/签名/公钥/分区哈希）16 组：0 命中
- 模式字段 key × 全部 IV 窗口 + 字节序变体：1976 组 0 命中
- loader1/2/3、postboot1、music 分区均为密文（熵≈7.8-8.0）
- **AES 密钥扩展表内存取证（自研 aes_schedule_scan.py，numpy 向量化，AES-128 44 字校验）**：
  program 转储 30.9MiB、128MiB 基线、新转储低段 RAM `ram_low.bin`(0x80000000-0x86280000, 99MiB) —— **全部 0 命中**。
  → 载荷解密很可能走**硬件 AES**，软件 RAM 中不存在持久密钥扩展表。
- PCM 明文音频扫描（pcm_hunt.py）：RAM 中仅有 32-64KiB 的零散音频样区，无完整音效库。

### 由此确定的路线
A. 版本检查绕过 + 官方 V2.9 包触发升级 + 0x5c 捕获分区对象+0x34（版本打印串 `Version : %x.%02x` @0x86847bd2 可查）。
B. 放弃拿 key，改做 RAM 代码执行，直接调用机内解密/音频函数。

## 15. 版本伪装成功 + 代码注入两次失败的教训（2026-11-18）

### 版本检查绕过（已验证成功）
- 升级包版本字段：`0x1c`、`0x1e`（头部）与 `0x2bc`、`0x2be`（签名元数据镜像），V2.8=0x80、V2.9=0x90。
- 改为 `0xA0` 后相机显示"固件更新到 2.A"并允许进入"开始更新? 是/否"。
- 生成文件：`S5___V30_versiontest.bin`（仅 4 字节版本差异，载荷完全未动）。
- **升级菜单只有在"拔 USB + 正常模式"下可用**；插线/服务模式会置灰。同版本不会被置灰，而是提示已安装。
- 进入 Yes/No 即证明验签 RAM 补丁对修改后的元数据有效。

### 代码注入尝试
1. `inject_test.py`：24 字节 Thumb 钩子，Capstone 反汇编 + Unicorn 仿真全部通过（寄存器保持、正常返回）。
   真机部署到 memcpy(0x866c22b4) 时**相机死机**：0x9c 每次只能写 2 字节，4 字节 b.w 补丁写到一半被 CPU 执行。
   → **热函数禁止用多 halfword 补丁**，必须单 halfword 原子写入或选冷函数。
2. `inject_cold.py`：钩子放 0x862f3000（22KB 全零区）。重启后 cave 全零、target 补丁仍在。
   → **全零空洞是 BSS，开机会清零，不能当代码洞穴**。
3. `inject_cold3.py`：钩子放 rodata 字符串 0x8708619a。重启后 cave、target、counter **全部恢复原厂**。
   → **主核镜像开机时重新加载，RAM 补丁不能可靠跨重启保留**（此前的"保留"只是偶发热启动残留）。

### 结论
服务模式（按键组合开机，可 USB 读写内存，更新菜单灰）与正常模式（可更新）无法共存，
且补丁无法可靠跨重启 → **必须在同一次服务模式会话内完成注入与触发**。

### 新线索：服务命令由 Linux `usb_mem` 内核驱动处理
- 设备节点 `/dev/usb_mem`；`/etc/init.d/usbgadget` 中 `usb_mem_module_name=usb_mem`（内建，不在 extra/*.ko）。
- 主核 program 中搜不到 0x5c/0x9c 分发器，证实读写由 Linux 侧实现（共享物理内存）。
- 下一步：枚举 usb_mem 命令集（是否还有 call/exec/update 之类操作码），或实现单 halfword 原子热补丁。

## 16. 三次真实刷机与密钥捕获结果（2026-11-18）

### 关键机制确认
- **电源键热重启可保留 RAM 补丁**（钩子、验签补丁均验证存活）；**拔电池则全部丢失**。
- 代码洞穴必须避开 BSS（开机会清零），rodata 字符串区可用。
- 热函数（memcpy）不能用多 halfword 补丁，会执行到半成品指令导致死机。
- `preflight.py` 做刷前全项检查；曾拦下"验签函数仍指向 AES 钩子洞穴"的致命遗留。

### 三次刷机
1. v1（4 字节版本差异）：显示 2.A，秒刷，三计数器 0。
2. v2（+构建日期 2 字节）：仍秒刷，三计数器 0。
3. v3（+music 分区 1 字节密文）：进度约 1/4 后提示关闭相机，三计数器仍 0。
三次刷机后钩子代码与跳转均完好，相机工作正常，版本仍 2.9。

### 结论
主核 `program` 中的软件 AES（0x868550ec / 0x86855116 / 0x868c0612）在升级全程**均未被调用**。
推测**真正解密与写闪存由 Linux 核完成**，主核只负责更新 UI。
因此改为在刷机之后重新转储低段 RAM（ram_after_updates.bin）扫描残留的 AES 密钥扩展表。
