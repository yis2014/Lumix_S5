# Panasonic DC-S5 2.8 / 2.9 与 S 20–60 镜头固件：第一阶段离线分析

## 结论

已实际读取并分析三份本地二进制，完成机身升级容器和48项分区目录解析、CRC32核验、版本间摘要字段比较，以及镜头型号识别。**没有解密机身程序，没有找到可用的功能解锁补丁或实时 LUT 内录实现，没有生成可刷改包。** 所有原始固件保持不变。

能够继续逆向研究，但目前不能承诺解除限制或在原代 S5 内录视频中烧录自定义 LUT。此阶段完成的是容器分析，不是代码级反汇编完成。

## 2. 机身容器：已验证结构

两版相同：

- 0x000：`UPD\0`。
- 0x00C：`MC801` 平台字符串。
- 0x038：小端数值 0x200，和外层头长度吻合。
- 0x03C：小端数值 0x0560EC00 = 文件长度 - 0x200。
- 0x040：外层数据 CRC32。计算 `zlib.crc32(file[0x200:])`，V28=0x6A0B11C8，V29=0x8E73AAC0，均精确匹配原字段。
- 0x200：`panasonic`。
- 0x220–0x25F：64字节高变化数据，未确认其密码学语义；不能仅凭长度宣称已证明 ECDSA。
- 0x2A0：重复的 `UPD` 头。
- 0x2E0：0x1400；对应分区数据相对于0x200基址的开始。
- 0x2E4：0x0560D800；加0x1400等于0x0560EC00。
- 0x2E8：48。
- 0x2EC：第一项分区名称，条目步长0x5C（92字节）。

以 `p = 0x2EC + index * 0x5C` 为基准，实测布局：

| 相对 p 偏移 | 长度 | 解释及证据 |
|---|---:|---|
| +0 | 12 | ASCII分区名 |
| +12 | 4 | 小端包内相对偏移 off；实际文件位置为 0x200 + off |
| +16 | 4 | 小端分区大小 |
| +20 | 4 | 目标/逻辑地址候选，不能当成文件偏移；具体运行时语义未核实 |
| +24 | 4 | 标志值，样本为2或3；不预先赋予完整语义 |
| +28 | 32 | 摘要字段：标志2区可独立核验为对应数据SHA-256；标志3区尚未确认其输入 |
| +60 | 16 | 附加字段，可能与封装/加密参数有关，未证实为IV |
| +76 | 16 | 尾部字段，本次不赋予确定语义 |

48项的实际数据范围首尾连续（允许零长 storage），末项结束为0x0560EE00，恰等于文件长度，没有越界。首项 loader1 实际从文件0x1600开始。注意不能把逻辑地址当作包内偏移，也不能忘记0x200基址。

### 2.1 标志、摘要与编码特征

- 标志2共有7项：storage（零长）、history、lens_hist、fileinfo、ninsho_db、wifi_info、menu_save。对应数据的SHA-256全部匹配目录字段。这些非空区在样本中是常量填充，不能称之为真实用户设置或已导出的机内EEPROM。
- 标志3共有41项。非空区普遍接近8 bits/byte，按原始数据计算SHA-256均未匹配目录摘要字段。
- 所有扫描到的 gzip 三字节候选均经解压验证失败，不能当成已找到的压缩文件。
- 未找到可直接识别的ELF、SquashFS、FDT等所检索魔数。
- `zboot`、`dtb`、`zimage`、`rootfs1/2` 是目录命名线索，与Linux式组件组织相容，但不构成已经解出Linux内核或确定CPU架构的证据。
- 高熵、摘要不匹配以及版本间附加字段变化，支持存在受保护/编码载荷的假设；**不足以证明具体AES模式、密钥长度、签名算法或安全启动实现。**

## 3. 2.8 与 2.9 的可验证差异

- 文件大小相同，48项分区的名称、偏移、大小及标志相同。
- 不同字节87,400,559，占96.8551%。这不是“97%的功能代码重写”的证据。
- 只有9项的目录32字节摘要字段变化：
  - program
  - postboot1
  - postboot3
  - postboot5
  - eep_fix
  - osdover
  - zimage
  - rootfs1
  - rootfs2
- 其余39项摘要字段相同。对标志3而言仍未解出其摘要输入，不能把这个统计提升为已经证明的明文代码差异清单。
- 大量摘要相同的标志3分区原始字节仍变化，附加16字节字段也变化，说明直接十六进制diff不能定位功能开关。

## 4. 镜头 PLF

与机身 UPD 是不同格式：

- 0x000：`LENS-UPDATE-FILE-SOF:`。
- 0x058：`LENS-UPDATE-FILE-EOH:`。
- 存在 `PSLFDH`、`PSLFDI`、`PSLF00` 等结构标签。
- 0x0B0 与0x582C4存在 `CABRIOLET`，仅视为内部标识。
- 0x4822E开始存在 `LUMIX S 20-60/F3.5-5.6` 型号文字。
- 0x48337存在 `Panasonic`。
- 全文件熵约6.7919，包含明显明文与结构化数据，比机身高熵区更容易展开。但尚未确定指令集、校验规则及完整段表。

镜头控制器与机身视频处理链分属不同固件；没有证据显示修改镜头PLF能为机身新增实时LUT录制。镜头仍涉及对焦、光圈及校准安全，不应随意修改刷写。

## 5. 对目标功能的判断

### 5.1 解除软件限制

需先明确具体限制：录制时长、地区帧率、码率、HDMI、菜单等对应不同代码路径。有些限制还涉及硬件、散热或传感器读出，不能都视为一个软件布尔开关。

当前已识别可优先研究的程序与资源分区，但尚无可读代码、可控执行入口、修改包可加载证据或可靠恢复路径。只改版本字段或重算外层CRC32，不代表相机将接受或能安全运行修改固件。

### 5.2 实时 LUT 内录

应严格区分：

1. 屏幕/取景器上的LUT监看。
2. HDMI输出是否带LUT。
3. 外部录像机将LUT烧进它录制的视频。
4. 相机自身编码前应用LUT，并将效果写入SD卡视频。

用户目标按第4项理解。即使确认监看支持LUT，也不自动证明可将其接入编码分支；需要研究图像缓冲区、处理节点、色彩空间、LUT插值、吞吐和编码输入路径。将监看LUT改接到编码器既不能仅从菜单文字得出，也未必仅是解除一个禁用开关。

目前没有找到此样本内的可验证LUT模块或现成补丁。随机高熵区中偶见 `LUT` 字符串属于弱/偶然命中，不作为功能证据。也不能由尚未解密推出“硬件绝不支持”。

## 7. 建议的下一阶段

1. 保持原件与恢复环境，先继续只读研究；本阶段脚本与指纹已保留。
2. 审核受保护分区封装：检查相同摘要分区跨版本关系、附加字段来源及升级执行链，而非暴力猜密钥或直接刷猜测补丁。
3. 查找可信公开代码、处理器资料及可合法获取的运行时证据。若需要拆机、串口或读取实体设备，另行明确操作与风险，不在本阶段自动进行。
4. 获得可读程序后，才能检索LUT加载/监看路径并判断与编码链的连接方式。
5. 如目标是尽快得到带LUT的视频，可评估在电脑端捕获普通HDMI并实时应用LUT后编码，或确认具体外录设备支持的LUT烧录模式；这属于外部处理方案，不是S5机内解锁，需核实色彩空间、位深、帧率、延迟和设备兼容性。
