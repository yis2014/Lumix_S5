# LUMIX S5 A 线突破记录（2026-11-19，主核被动借用路线证伪后）

本轮把 "主核代码执行实证" 推进为 "可用武器 + 机身验签可绕过 + StcStream/NAND 结构定位"。

> **03:11 续作状态：A1–A4 全绿，任意函数 detour 已多次独立验证；但“SD 更新必经 `0x87F4D32E`、可借其 NAND 对象”的假设已被实机证伪。相机已用完整官方 V2.9 包刷回，主核补丁、版本结构和 cave 均恢复原厂。后续不得重复主核菜单触发，应转向 postboot 早期插桩或 UART。**

以下地址除特别注明 "物理" 外，均为 **0x5c/0x9c 服务别名**（物理 = 别名 − 0x80000000）。

## 一、运行时地址映射（本轮确证，工具链的基础）



* CPU 运行时使用**物理地址**：代码 `0x06xxxxxx`、栈 / 堆 `0x09xxxxxx`、堆 `0x08xxxxxx`。

* 服务 opcode `0x5c/0x9c` 使用 `+0x80000000` 别名（如 detour 目标 `0x868C5E48` ↔ 物理 `0x068C5E48`）。

* **正常模式的栈 / 堆对象在回服务模式后被销毁**（读出 `0xefefefef` poison 或全 0）。

  要抓对象，必须在 hook 执行瞬间把内容写进 BUF；rodata（vtable / 常量）回服务后仍可读。

* **绝不可拔电池**：拔电池会清空全部 RAM 补丁（detour/hook/BUF/counter）。热重启保留补丁。

## 二、payload 工具链（成熟，可复用）



* `lumix_ml/build_dump_payload.py`：keystone 两遍汇编（分支目标写**裸地址不带 #**）+

  Capstone 反汇编 + Unicorn 仿真自测 + `--write` 部署（write\_mem\_safe 自动备份 + 读回校验）。

* `lumix_ml/read_dump.py`：读取 BUF/counter，解析 r0/r1/r2 对象与 vtable、调用者。

* 当前 detour：目标 `0x868C5E48`（镜头 LENS-UPDATE 文件头解析），补丁 `c0f35ab2` → CAVE `0x87086300`。

  BUF `0x87086400`：+0 regs (6 dword)、+0x20 r0 对象、+0x30 r1 对象、+0x40 r2 对象；COUNTER `0x87086450`。

* 触发流程：热重启进正常模式 → 官方 `400BV020.plf` 点镜头更新（提示 "已安装"）→ 热重启回服务 → `read_dump.py`。

## 三、机身验签可绕过（本轮最大武器）



* **镜头验签包装&#x20;**`0x868C08C6`：memcpy 签名 (r||s)/ 公钥 (x||y) → 调 **ECDSA 核心&#x20;**`0x868CA60E`。

  `0x868CA60E` 是软件 P-256 ECDSA 验证（bignum 库 `0x868CD6DE`/`0x868CD6F0`，EC 运算 `0x868CE4D2/0x868CE7B2/0x868CE856`）。

* **机身也调用同一个包装**：机身验签函数（`0x868AE5D2` 处 `bl 0x868c08c6`）。

  即 **机身 25% 验签 = 软件 ECDSA，与镜头同套**。

* **绕过方法**：把 `0x868CA60E` 改为 `movs r0,#1; bx lr`（或让包装恒返回 1），镜头 + 机身验签同时通过。

  `find_callers(0x868CA60E)` 仅 `0x868C0916`（包装内），证明这是唯一验签核心。

* 机身 ECDSA 公钥：`0x868AE7F0`（0x40 字节，由 `0x868AE5B8` 的 `ldr r1,[pc,#0x234]` 加载）。

* 软件 SHA-256：`0x868C3384`（升级包 hash）；SHA-256 K 表 `0x86F52AB0`。

## 四、StcStream / NAND 结构



* **StcStream NAND 子类构造器&#x20;**`0x8685507C`：`ldr r1,[pc,#0x2f8]` 取 vtable 基址（存于 `0x86855378`），`+0x28` 得 vtable。

* **vtable =&#x20;**`0x86F50404`（物理 `0x06F50404`），20 项虚函数（`0x86855099…0x868552E7`），

  其中 read 类 = `0x86855116`(调 `0x868C0612`)/`0x86855152`(调 `0x868C05B2`)。

* 机身验签函数（`0x868AE400…`）流程：StcStream 读包（`0x865D3xxx` 包装群）→ SHA-256 → ECDSA 验签

  → 验签通过后写 NAND 暂存（`0x8685507C` 等流操作）。**全程无 AES 调用**。

* **结论：机身包主核只验签（对密文）、不解密；AES 密钥在 postboot（引导程序）。**

* `0x865D3xxx` 是包装层，按运行时标志分发到 `0x863Exxxx` / `0x865D2xxx` 两套后端，NAND 控制器操作在更底层。

## 五、主核软件 AES（镜头专用）



* AES SubBytes `0x868C06FE`（S-box 查表）；**AES S-box&#x20;**`0x86F50454`（`63 7c 77 7b …`）。

* S-box 物理地址 raw32 引用于 `0x868C072C`。StcStream 读取镜头包时实时 AES 解密。

* 机身不走此 AES 路径（机身验签函数无 AES 调用）。

## 七、原下一步方案（2026-11-19 03:11 已证伪，不再执行）

NAND 驱动链已摸清（本轮新增）：



* **NAND 设备 open&#x20;**`0x87F4D0FE`：`open(dev_mgr, param, ctx)`，内部 `adr r1,#"NAND"`。

  调用者 `0x87F1FDF8 / 0x87F337EC / 0x87F4DA9C` 证实参数来自**运行时设备管理器对象**

  （`[obj,#4]`、`[obj,#0x240]`），**无法在 hook 里盲目构造，硬调会死机**。

* **NAND 分区读写包装&#x20;**`0x87F4D152`：范围检查后 `b.w 0x8782BD04`。

* `0x8782BD04` = **ARM 长跳转桩**（`bx pc` 切 ARM + `ldr pc,[pc,#-4]`），真实目标 `0x866C22B4` = **memcpy**。

  即 **NAND 分区读 = 内存映射后 memcpy**；NAND 底层含 **ARM 代码**（Thumb 反汇编会读出乱码，需 CS\_MODE\_ARM）。

* **主动读 NAND 的正确方案（被动借对象）**：detour 钩住 NAND 读函数（如 `0x87F4D152`），

  正常模式升级（镜头 / 机身）使其被调用、传入**有效设备对象**；在 hook 里**借该对象额外读 postboot 分区到 BUF**，

  回服务模式读取。这样不需要自己构造设备管理器，安全可行。

执行步骤：



1. 对 NAND 读函数 `0x87F4D152` 下 detour（复用 build\_dump\_payload 改 TARGET），抓设备对象与分区参数。

2. 在 hook 里用抓到的有效对象调读函数，把 postboot 分区读进 BUF，dump 整机 NAND。

3. 从 NAND dump 找 postboot 明文 / 密钥派生数据 /boot ROM，提取机身 AES 密钥。

4. 验签绕过已就绪：需要时把 `0x868CA60E` 补丁为恒真（镜头 + 机身同破）。

## 八、已验证死路（勿重复）



* 符号字符串 xref /raw32 引用（全 0）；连续代码地址符号表（不存在）。

* 服务模式解析 NAND 设备对象（`G=0x0C1EF828` 全 0，NAND 框架未初始化）。

* key\_oracle 扫 RAM 找机身 AES 密钥（0 命中，密钥确在 postboot）。

* 从参数对象抓 vtable（校验函数参数是 C 结构，非多态对象；且回服务后对象销毁）。

* `0x868C0924` 不是密钥指针（小数值 0xE7FB，误读）。

## 九、03:11 续作：主核被动借用路线实测与纠偏

### 9.1 新 payload 与离线验收

* `lumix_ml/build_nand_read_probe.py`：针对 `0x87F4D152` 的 92 字节只读抓参 hook；保存寄存器、LR 和 `r0` 指向的 32 字节流描述符。Capstone + Unicorn 通过，含无效指针跳过、寄存器恢复与计数器断言。
* `lumix_ml/read_nand_dump.py`：服务 USB 只读读取器，原始结果写入 `analysis/nand_read_capture_latest.json`。
* 静态确认 `0x87F4D152` 只有一个 `r0` 流对象参数，只有两个直接调用点 `0x87F4D576 / 0x87F4D5A2`，均位于函数 `0x87F4D32E` 内。
* `lumix_ml/build_fwupdate_entry_probe.py`：针对 `0x87F4D32E` 的 126 字节入口 hook，复制静态 `G/S` 后令 `r0=1; bx lr`，利用唯一调用者现成的错误分支，不执行 worker 函数体。仿真通过。
* `lumix_ml/read_fwupdate_entry_dump.py`：读取入口抓参结果。部署新 payload 前均恢复旧 detour，避免两个入口共用同一 cave 而跳入错误代码。

### 9.2 实机结果：所有有效触发均未进入 worker

1. 镜头官方包“已安装”流程：NAND 计数器 0；目标与 cave 在热重启后仍完整。
2. 机身 2.A 单版本修改包：worker 计数器 0。发现元数据验签尚未绕过后，临时部署 `0x868C08C6 = 00 20 70 47` 再试，仍为 0。
3. 用户澄清：v1 与 versiontest3 的实际表现几乎相同，都是秒刷；旧记录“v3 才能走到约 25%”不准确，**不得再用它作为选择测试包的依据**。
4. 恢复原厂验签，把 `0x863B0000 / 0x863181E2` 的 RAM 版本临时改为 2.0，使用完全未修改的官方 `S5___V29.bin`。相机完成官方更新并回到 V2.9；worker 仍未被捕获。
5. 官方更新后读取：worker 恢复 `2de9f04f...`，验签恢复 `70b5b0b0...`，版本恢复 `90029002`，cave 恢复为字符串 `...object has set ios::failbit...`。这证明完整更新会重载主核镜像并清除本轮 RAM hook。

`fwupdate_entry_capture_latest.json` 中最后一次非零“计数器”和 `0x3e.../0x3f...` 数据是 cave/BUF 被重载后的无意义内容，**不是有效 G/S，不得用于反汇编或参数推断**。

### 9.3 真实 SD 更新链与 postboot 结论

* 真实机身验签函数为 `0x868AE53E`，唯一调用点 `0x8689A67C`；它在主核中完成包验证并安排后续流程，不是 `0x87F4D32E`。
* `0x868AE53E` 在验签后确实构造 AES/StcStream 对象，但 `0x868AE5EC` 的设钥字面量指向物理 `0x06F5038C`（服务 `0x86F5038C`），内容仍是重复的 `0123456789abcdef` 占位材料，**不是机身真实 AES 密钥**。
* 官方包完整刷写成功而 worker hook 从未命中，结合调用链可判定：`0x87F4D32E` 不是 SD 卡机身更新的必经 worker；真正解密/刷写发生在后续 postboot，主核被动借用方案关闭。

### 9.4 服务模式对象与官方更新后低 RAM

* 直接读取静态对象：`G=0x0C11DA38` 在服务别名 `0x8C11DA38` 仅部分初始化，`S=0x0C2110A4` 全零；`G` 的设备上下文字段仍为空，不能据此盲调 NAND 驱动。
* 新只读转储：`lowmem_after_official_v29.bin`（`0x80000000–0x80200000`）。与旧 `lowmem_0_2M.bin` 仅 31,616 字节不同，差异主要为零散运行时数据。
* AES-128 调度表扫描 0 命中、S-box 0 命中、已知明文 `key_oracle` 0 命中。官方更新后的低 RAM 仍未留下可直接利用的机身密钥。

### 9.5 当前安全状态与下一步

**当前相机为官方 V2.9，原厂验签、原厂版本结构、原厂 worker 和原厂 cave；本轮主核 RAM 补丁均已被官方更新清除。**

后续只推进以下方向，不再重复主核镜头/机身菜单触发：

1. **纯软件路线**：分析低 RAM Reset/postboot 早期执行链，研究在主核镜像重载之外保存早期 hook 与带 magic 的捕获区；先证明热重启存活和触发点，再考虑 NAND 只读。
2. **UART 路线（高价值备选）**：依据现有 DTB/bootargs 的 `console=ttyAMA,115200` 线索，接 UART 控制台验证是否可直接取得 shell/引导日志。需用户明确选择硬件操作后再执行。
3. 任何后续 payload 必须增加 magic/格式版本，读取器先验证 magic 再解释数据，避免把重载后的随机缓冲区误当有效捕获。

## 十、高内存最终增强重扫

三段转储已合计覆盖完整 `0x90000000–0xA0000000`（268,435,456 字节）：原有 `highmem_9000_a000.bin` 实际只到 `0x98CD2000`；USB 断连前的 17 MiB 保存在 `highmem_98cd2000_a0000000.bin`；随后从 `0x99DD2000` 续传至 `0xA0000000`，保存为 `highmem_99dd2000_a0000000.bin`。

新工具 `lumix_ml/aes_schedule_rescan.py` 已通过 FIPS-197 标准向量与 AES-128/192/256、大小端往返自测。完整高内存按 **AES-128/192/256、大小端、4 种字节对齐**重扫，最终 **0 个有效密钥调度表候选**。没有候选可做已知明文验证，未拿到机身 AES 密钥；该结论不再受旧扫描器字节序问题或断连未跑完影响。
