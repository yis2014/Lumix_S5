## 1. 下一步（按优先级）
**A. 把计数器 hook 升级为功能 payload（总钥匙路线）。**

  读 MMIO / 调主核函数 / 把指定区域复制到 RAM 缓冲区（如 `0x8F000100` 暂存区）再用 `0x5c` 拖回 PC。

## 2. 本轮两条血泪教训（务必记住，别再踩）
1. **热点 ARM 函数不能打补丁**：memcpy(`0x866C22B4`，ARM `cmp r2,#3`…) 每秒被调上万次，而 `0x9c` 一次只写 16 位，32 位补丁要分两次写，中途被调用就会执行"半新半旧"指令 → 必死机。**只能打冷函数**（空闲时慢慢写，无竞态）。
2. **全零 BSS 区会被系统运行时抹掉**：第一版 hook 放 `0x86300000`（全零区），结果被系统清成 0。**hook 和计数器必须放 rodata**（加载镜像、能存活、系统不改写、我的 hook 又能写）。
   - 佐证：`0x868C08C6` 的补丁一直存活，而 `0x86300000` 的 hook 被抹成 0。

## 3. 核心能力与已验证事实（沿用）
- **Service USB**：`VID_04DA&PID_2370`；`0x5c` 每次读 1 KiB，`0x9c` 写 16-bit halfword（需逐个读回重试）。**只在服务模式可用**；后台/多进程访问会失败，长操作前台小块执行。
- **OSD 已验收**：Plane A `0x8DC00000`，stride 4096、宽 1024、`x=64,y=48`、SCALE=4。
- **官方固件刷写**：把机内版本结构 `0x863B0000` / `0x863181E2` 改成低版本（如 `00 02...`=2.0），即可刷入更高官方包。当前 V2.9 结构读回为 `9002...`。
- **内存别名**：`addr` 与 `addr+0x80000000` 同物（`0x0↔0x80000000`、`0x10000000↔0x90000000`）。虚拟地址 = 物理 − `0x80000000`。
- **主核明文**：`0x86280000–0x88000000`（V2.9 dump `program_0x86280000.bin`，30,932,992 字节）。**主核只有一套 AES（全部服务镜头升级）**，机身 AES/验签在引导程序里。
- **引导程序把分区解密加载到固定 RAM**：rootfs1 `0x83100000`(3MB squashfs)、rootfs2 `0x83400000`(10MB squashfs)、program `0x86280000`。两个 rootfs 已在 Linux 云主机解包（`~/lumix/rfs1`、`~/lumix/rfs2`）。
- **设备树**：GIC `0x70001000`、SP804 `0x7F02A000`、**PL011 UART `0x7F050000`（bootargs `console=ttyAMA,115200`，status=okay）**、SDIO `0x7C300000/302000/304000`、USB DWC3 `0x7C200000`。
- **镜头密钥**：设钥 API `0x868C69EC`，字面量指向 `0x08AB4E88`/`0x08AB4E98`（两段 ASCII 密钥材料）。这些**对机身分区无效**（已用预言机排除全部候选与算法组合）。
- **机身 program 分区**：包内载荷 `0x17E00`，分区头 IV `934a5593c377bc856ded60c01ac18e2c`，已知明文前16字节 `70f09fe5b02f10ee032002e29f00a0e3`（预言机）。
- **music 分区**：包偏移 32,117,760，大小 3,538,944 字节；主核无机身 AES 却要用 music → **music 在 RAM 中很可能已是明文**（改快门音或可不靠密钥）。
- **高风险**：`0x932F0C00` 曾致掉线；`0x90000000–0xA0000000` 是实时视频 DMA，勿乱写；`0x61` 操作码曾致服务接口暂时失联（后自恢复）。

## 4. 已验证死路（不要重复）
静态密钥穷举、RAM AES 扩展表扫描、主核 AES/UPD 挂钩捕获、主核镜头验签绕过、镜头密钥全组合、拔电池后 RAM 持久化、把低地址当新物理区、从 rootfs 找 Flash 工具、热点函数打补丁、全零 BSS 当代码洞、
**detour 打在镜头验签包装 `0x868C08C6`**（只在"文件版本>已装版本"才调用，官方同版本包永远绕过 → 计数器恒 0；应打更上游的头部校验函数 `0x868C5E48`）、
**高内存 `0x90000000–0x98CD2000` 找 postboot**（2026-11-19 全扫：无 AES S-box/P-256/异常向量/引导字符串，大片 100% live 区只是视频帧缓冲）。

## 4.1 低 RAM 引导区新发现（2026-11-19）
- **`0x80000000` 起常驻明文 ARM 启动代码**（已在 `lowmem_0_2M.bin`，2 MiB，97–99% live）：
  异常向量表为 `b` 跳转形式，Reset→`0x80000050`（关 IRQ/FIQ、关 cache/MMU、SP=`0x13000`、读 MPIDR 分核）。
  → "引导程序明文只在 NAND"需修正：**启动/底层代码开机后常驻低 RAM 且已 dump**。
- 该区域字符串含 `panasonic,pvc03v` 与完整 DTB（`0x80120800`，与 `dtb_120800.bin` 同一份；
  两dump间尾部 0xAA 填充区有随机差异，无意义）。DTB 仅 GIC/timer/UART/SDIO/clocks，**确无 NAND/crypto 节点**。
- **`0x7C015000` = GPIO/pinmux 类控制器**（按位号 set/clear `[+0x1e8]/[+0x1ec]`、引脚配置表查找），不是 NAND/AES。
- 该 2 MiB 无 AES S-box → 若机身 AES 由引导程序完成，**很可能是硬件 AES 引擎**（这解释了历次软件密钥表扫描全灭）。
- 教训：扫 MMIO 常量时 DTB 的**大端属性名偏移**（如 `00000068`）会被小端读成 `0x68000000` 假命中，需先排除 DTB 区。
