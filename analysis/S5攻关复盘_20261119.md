# Panasonic DC-S5 攻关复盘与下一阶段路线（2026-11-19）

## 0. 一句话结论
**机身升级的解密与验签都在引导程序（bootloader/postboot）里，不在主核 `program`，也不在 Linux 用户态。**
主核里那套 UPD + AES + P-256 代码是**镜头固件升级**用的（字符串 `LENS-UPDATE-FILE-SOF/EOH` 证实）。
因此：**要拿 AES 密钥 / 绕过机身验签 / 改 music 快门音，都必须先拿到引导程序明文，而引导程序明文只存在于 NAND。**

### 版本伪装刷机法（重要成果）
- 机内版本结构：`0x863B0000` 与 `0x863181E2`，内容 `90 02 90 02 10 07 50 14`（版本+日期）。
- 改为 `00 02 00 02` → 机身显示 **Ver.2.0**（注意：显示可能要热重启后才更新）。
- 之后**任意官方升级包都会被当作高版本接受**，**签名天然合法**，可真正刷入。

- 恢复：直接刷官方 V2.9 即可（此时 2.9 是更高版本）。

## 2. 已排除的死路（不要再重复）
1. **主核 AES/UPD 函数挂钩抓密钥**：A/B/C/D 四钩子全部零触发。因为那是镜头升级代码。
2. **主核验签包装 `0x868c08c6` 改返回 0**：对机身升级无效（那是镜头验签）。
3. **静态密钥穷举**：UPD 头/分区表窗口、CTR/CBC、IV、字节序、取反组合 13,666 组、哈希派生、AES 常量区 8,514 组，全无命中。
4. **AES 密钥扩展表扫描**（aeskeyfind 式）：主核转储、128 MiB 基线、99 MiB 低段、三次刷机后 RAM、低地址 0–64 MiB，**全部 0 候选**。
5. **CTR 密钥流跨分区复用**：失败。UPD 头 IV 全 0，但**各分区独立密钥**（key 来自分区对象 `+0x34`），不能互解。
6. **Linux 侧 AES**：全部属于 OpenSSL（TLS 密码套件）、MTK 蓝牙（`blueangel/btcore`）、Wi-Fi PSM，与升级无关。
7. **低地址 0x0–0x4000000**：与 `0x80000000+` 是**同一块物理内存的别名**，并非新区域。

## 3. 内存地图（重要）
- **别名规律**：`addr` 与 `addr + 0x80000000` 指向同一物理内存。
  - 实证：`0x0` 与 `0x80000000` 都是 ARM 异常向量表；`0x10000000` 与 `0x90000000` 都是 `CDNN...`。
- `0x86280000–0x88000000`：主核 RTOS `program` 明文（30,932,992 字节已转储）。
- `0x80000000–0x86280000`：Linux 内核/用户态 + 协处理器固件（蓝牙等）。
- `0x88000000–0x90000000`：stage2/堆，无 AES S-box。
- `0x90000000–0xA0000000`：视频 DMA / 部分未使用（大量 `0x55`），**尚未完整扫完**。
- `0x8DC00000` / `0x8DF00000`：OSD Plane A/B。
- `0x8F000100`：高 RAM 暂存区（部署前为 `0x55` 填充），曾用作钩子密钥缓冲。

## 4. 关键技术结论
- **机身验签真实存在**：机内版本合法 + 仅改 1 字节 → 仍 25% 中止；官方包 → 成功。对照明确。
- **机身升级分两段**：正常模式暂存 + 校验（25% 处为校验点），**真正解密写入在下次开机的引导阶段**。
  - 推论：刷完**必须先正常开机一次**，直接进服务模式可能跳过升级流程。
- **镜头升级代码在主核**：`0x868c6000–0x868c7000` 区域，含 UPD 解析、AES-CTR、P-256 验签。
  - 设钥 API：`0x868c69ec` → `memcpy(对象+0x34, 密钥指针, 长度)`，**密钥由调用者传入**。
  - 读数据+按字取反循环：`0x868c6ac4`（受 `[对象+0xC]` 控制）。
- **真机代码注入仍未被证明**：钩子能仿真、能跨热重启保留，但从未被触发。
- **热重启保留 RAM 补丁，拔电池全部清空**；BSS 开机清零，rodata 可跨热重启。

## 5. 工具与环境坑（务必记住）
- **后台任务里 USB 读取会全部失败**；前台单读正常。
  → 凡是要跑超过 ~15 秒的 USB 扫描，必须**切成小块在前台执行**（每次 ≤16 个 1 KiB 读）。
- **`Select-Object -Last` 会把输出全部缓冲到命令结束**，长任务务必 `*> 日志文件` 再读日志。
- **不要同时开多个进程访问同一 USB 设备**，会互相挤掉导致全灭。
- `0x932f0c00` 曾导致 `err=22` 掉线；`0x90000000+` 含实时视频 DMA，写入危险。

## 6. 下一阶段路线（按优先级）
### A. 拿到引导程序明文（总钥匙）
1. **扫完 `0x90000000–0xA0000000`**：postboot 可能常驻于此，是最后一块未扫区域。
2. **静态追踪镜头设钥 API 的调用者**（`bl_xref.py` → `0x868c69ec`），确认密钥是否硬编码在主核；
   若机身与镜头共用密钥体系，可直接命中。
3. **NAND 读取**（最终手段）：Linux 有完整 MTD（273 处字符串）与 `usb_mem` 驱动；
   需要定位 NAND 控制器的内存映射寄存器，用 `0x9c`/`0x5c` 驱动它读出 postboot 与 music 明文。
   ⚠️ 只在确认寄存器语义后操作，避免误擦写。

### B. 机身验签绕过（比拿密钥更关键）
- 即使拿到 AES 密钥，改包仍会被验签拦下。
- 但**若能绕过验签，可以把分区头加密模式字段（`+0x34==2`）改为 0，直接写入明文分区**，
  **完全不需要 AES 密钥**即可改 music / program。
- 两条路：替换 P-256 公钥为自己生成的（可自签任意包）；或让验签函数直接返回成功。

### C. 快门音（最终目标之一）
- 播放链已明确：`AUDIO_PlaySound` → 消息队列 → `AUDIO_soundplay_task` → `avio_audio_soundplay_cb`
  → `audio_soundplay_get_data(id,freq,adr,size)` → `VclPCMOneShotPlayManager`。
- music 分区在 **NAND 中是明文**（升级时解密后写入），**读到 NAND 即可直接改声音**。

## 8. 第二轮突破（2026-11-19 续）
### 8.1 密钥提取方法已打通（可复用）
链路：`bl_xref.py` 找设钥 API 调用者 → 反汇编取密钥指针字面量 → Service USB 读出密钥。
- 镜头设钥 API：`0x868C69EC`（`memcpy(对象+0x34, key, len)`），两个调用者：
  - `0x8686757E`：`ldr r1,[pc,#0x1d4]` → 字面量 `0x86867750` → 指针 **`0x08AB4E88`**，长度 `0x10`
  - `0x868C7486`：`ldr r1,[pc,#0x130]` → 字面量 `0x868C75B4` → 指针 **`0x08AB4E98`**，长度 `0x10`
- 读出的真实密钥材料：
  - `0x08AB4E88` = `WZdHXAXgu7Cn691V`
  - `0x08AB4E98` = `ML/k5tjaCr9zKjRfR`
- 二者是同一段 64 字符 Base64 风格密钥串的连续两段，区域另有
  `SMP/Cortex-A7/RVDS Version G5.6.1.5.1 / v2.0rel2.6` 版本串。
- **注意**：该区域内容在两次转储间有细微差异（`WZdHY...` vs `WZdHX...`），可能动态更新。

### 8.2 密钥预言机（已验证正确）
`lumix_ml/key_oracle.py`：以"解密机身 program 分区前 16 字节 == 已知明文"为判据。
- 已知明文：`70f09fe5b02f10ee032002e29f00a0e3`（`program_0x86280000.bin` 起始）
- 分区密文：`S5___V29.bin` 偏移 `97280+0x200`
- **分区 IV 在分区头 `+0x80`**（`934a5593c377bc856ded60c01ac18e2c`），**不是文件头的 0**。
- 加解密往返自测通过，故"无命中"均为真阴性。

### 8.3 已排除
- 上述两把镜头密钥，在 **AES-128/256 × CTR/CBC/ECB × raw/inv32** 全组合下均**不能**解密机身 program 分区。
- `0x08AB4000–0x08AB8000` 共 16 KB 全窗口预言机搜索：0 命中。
- `0x08AB0000` 附近为空（`@@@@```` 填充）。

## 9. 第三轮重大突破：DTB + 解密 rootfs（2026-11-19 再续）
### 9.1 体系结构真相（来自 RAM 中的设备树与内核日志）
- **CPU：ARM Cortex-A7**；Linux 直接运行在 RAM 中。
- **bootargs**：`root=/dev/mtdblock0 slram=slram0,0x83100000,+0x00300000,slram1,0x83400000,+0x00A00000 console=ttyAMA,115200 lpj=6213632`
- **MTD 是 `mtd-ram`（内存映射）**，路径为 `/virtual/mtd/mtd0..3`，**Linux 完全看不到真实 Flash**。
  → 真实 Flash 访问全部在**主核 RTOS / 引导程序**手里，NAND 驱动不在 Linux。
- **引导程序把分区解密后加载到固定物理地址**：
  - `rootfs1`（3 MB）→ **`0x83100000`**，squashfs（魔数 `hsqs` 已验证）
  - `rootfs2`（10 MB）→ **`0x83400000`**，squashfs（已验证）
  - `program`（主核 RTOS）→ `0x86280000`（早已转储）
- 硬件寄存器：**SDHCI `0x7C300000/0x7C302000/0x7C304000`**（后者 okay，为 SD 卡槽）、
  **USB DWC3 `0x7C200000`**、**PL011 UART `0x7F050000–0x7F054000`**、
  **GIC `0x70001000`**、**SP804 timer `0x7F02A000`**。
- DTB 位于 RAM `0x822FF000`（另有副本 `0x80120800`），已导出 `dtb_22ff000.bin`、`dtb_120800.bin`，
  解析器 `lumix_ml/dtb_parse.py`。**DTB 无 NAND 节点**（因 Flash 不暴露给 Linux）。

### 9.2 已产出的实物成果
- **`rootfs1_dump.bin`（3 MB）与 `rootfs2_dump.bin`（10 MB）：解密后的 Linux 根文件系统，未使用任何密钥，直接从 `ram_low.bin` 提取。**
- 设备树两份 + 完整硬件内存映射。

### 9.3 关键推论
- 主核按需读取 music，而主核无机身 AES → **music 必然也是解密后才被使用**（或开机时已加载入 RAM）。
- 直接读 Flash 基址（0x08000000/0x10000000/0x20000000/0x30000000 + 0x80000）**均未命中明文 program**，
  → Flash 中仍为密文，**明文只存在于引导程序加载后的 RAM**。
- **因此"拿 AES 密钥"与"拿到各分区明文"可以分离**：后者已经在 RAM 里，不需要密钥。
  真正仍需密钥/验签绕过的是**"重新刷回 Flash"**这一步。

### 9.5 rootfs 解包结果（已在 Linux 云主机完成）
- 工具：云主机 `apt-get install squashfs-tools`，`unsquashfs`；两镜像均为 **Squashfs 4.0 / LZO**。
- 解压目录：`~/lumix/rfs1`（主根）、`~/lumix/rfs2`（挂于 `/mnt/rfs2`）。
- **Linux 为从核**：`/etc/modules` 仅 `cpu_iccdrv`、`cpu_icsmdrv`（核间通信），通过 ICC 与主核 RTOS 交互，**不接触 Flash**。
- **无升级/Flash 工具**于用户态 → 升级与 Flash 全部在主核 RTOS / 引导程序。
- `lighttpd` + `cam.fcgi`（stripped ARM ELF，仅 FCGI 转发）→ 网页 API 实现在在主核。
- 内核 **3.18.18**；`MC801_allmenu.xml`（307 KB，1528 项）**无隐藏/服务菜单**。
- 新入口线索：`avio_evf_driver_read_eeprom()`（EVF 小 EEPROM，非主 Flash）、`Sdds_*`（SD 卡驱动）。
- **`console=ttyAMA,115200`**：设备带有 **PL011 UART 控制台**（`0x7F050000`，status=okay）。
  → **接 TTL 串口很可能直接拿到 Linux shell**，是绕过一切软件限制、读取 Flash/密钥的最高性价比路径。
- `audio_soundplay_get_data` 等字符串经字符串表间接引用，pc_xref / 指针扫描 / movw 均无法定位，
  主核 Flash 驱动无调试字符串，**纯软件逆向主核 Flash 驱动效率极低**。

### 8.4 机身与镜头是两套升级路径
`0x87F2D033`：`FW_UPDATE_MODE[IN] fw_ver=%s`（机身）
`0x87F2D058`：`LENS_FW_UPDATE_MODE[IN] fw_ver=%s`（镜头）
位于网络控制模块 `Netmw_set_wlv_camctrl_request` 的日志中，**机身升级走网络控制路径**。
→ 下一阶段：沿机身 `FW_UPDATE_MODE` 找其设钥点，用 8.1 的方法取机身密钥并用 8.2 预言机当场验证。
