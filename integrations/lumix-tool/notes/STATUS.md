# S5 固件改造 — 进展与结论（截至 2026-11-19）

## 已证实（都被真机验证过）

1. **容器目录可改，更新流程不拦。**
   把 `storage` 记录的目标地址从 `0x01240000` 改成 `0x016C0000`、重算外层 CRC32，
   相机照常弹「开始更新？」，进度条跑完，提示重启（约 10 秒），无报错。

2. **版本门在文件头 `0x1C`（u16×2），且相机不保存它。**
   - `0x0290` → 「存储卡上的固件版本已安装」
   - `0x0291` → 「开始更新？」
   - 刷完后机身仍显示 **2.9**，且「固件更新」仍可用
   → 版本号没有被污染，同一文件可反复刷。代价：每次要抬一格。

3. **「固件更新」菜单项只在开机后约 10 秒内可用**，之后一律变灰。
   这不是 CRC 拒绝：对照组 P0（官方内容 + 2.91 头 + CRC 完全正确）等 30 秒后同样变灰，
   而用「开机瞬间进菜单」又能点开并走到「开始更新？」。
   → 之前「开机校验整包 CRC」的结论**作废**。
   目前模型：开机窗口内菜单可用 → 点击时才用文件头 `0x1C` 与机身版本比较
   （2.91 → 「开始更新？」，2.90 → 「已安装」）→ 真正开始后才做 CRC/逐分区哈希校验与解密写入。

4. **`flags=2` 的 7 条记录**（storage/history/lens_hist/fileinfo/ninsho_db/wifi_info/menu_save）
   在容器里就是明文（全是 0x00），`sha256(数据区) == 记录哈希` 全部命中。

5. **`flags=3` 是密文**：长度与明文相同，10MB 分区内 16 字节块零重复 → 非 ECB；
   每条带 16 字节 IV（flags=2 时为全零）。

## 2026-11-20 重大进展：服务 USB 通道打通

- S5 进入工厂/服务模式的方法：**按住 `PLAY`(回看) + `AF-ON` 不放，再开机**。
  之后 USB 从 `04DA:2382`（PTP）变成 **`04DA:2370`**（厂商服务接口，ff/a0/b0）。
- Windows 侧用 Zadig 把 **WinUSB** 绑到该接口；注意 `CreateFile` 必须带
  `FILE_FLAG_OVERLAPPED`，否则 `WinUsb_Initialize` 返回 ERROR_INVALID_HANDLE。
- 接口 GUID 取自注册表 `Device Parameters\DeviceInterfaceGUIDs`
  （Zadig 写入的是 `{CDE53111-593A-43C9-AB10-EA9DACF2C573}`）。
- 已实现 `tools/s5svc.py`（纯 ctypes 调 winusb.dll，无需 pip）：
  - `probe-zero`（0x5C 空窗口）→ 返回 `01 00 FF 05` 成功头，块读处理器存在
  - `0x35` 索引缓冲读 → 选择器 0x20 索引 0 返回 `3067`
  - `0x75` RAM 相对字读 → 0x36 正常回复
  - `0x5C` 1KB 块读 → **可用**
- **`block 0x80000000` 读到了 ARM 异常向量表**（`12 00 00 EA ...`），
  说明 S5 的 RAM/启动镜像基址是 `0x80000000`，且这里是 32 位 ARM 代码。
- 已 dump `0x80000000..0x80200000`（2MB）到 `out/ram_80000000.bin`。
- 服务模式会因空闲自动关机（约 4–7 分钟），需要定时点击触摸屏保活。
- 容器结构与社区 GM5/GX8/GX9 的 UPD-v2 完全一致（每条 0x5C：name[12] + 4×u32 +
  sha256[32] + iv[16] + 保留[16]），加密极可能是 **AES-128-CBC 5 轮**，
  IV = 记录里的 16 字节槽。

### 正在做

- `tools/s5key.py`：用 eep_ow_a/eep_ow_b（明文相同、IV 不同）做无假定筛选，
  命中后用 loader1 的 SHA-256 验证；扫描 2MB dump。

### RAM 里直接就是明文（关键捷径）

- `0x80000000` 起 4MB 已 dump 到 `out/ram_80000000.bin`
- 用容器里已知的明文 SHA-256 在 dump 里做匹配，认出：
  - `0x80000000` **loader3**（0xC000）完整命中
  - `0x80120000` **zboot**（0x800）命中
  - `0x80120800` 处是 **FDT/DTB**（magic `d00dfed`），但和容器 `dtb` 分区的 0x1000 字节版本不完全一致（填充/裁剪差异）
- 结论：**相机启动时把固件解密后加载到 RAM**，明文可直接读，
  **不需要 AES 密钥**就能拿到代码。
- 读取速度：`--settle 0.001` 时约 **4ms/块 ≈ 250KB/s**（30ms 时只有 31KB/s）。
  1ms 间隔下连读 4000 块无错误。

## 2026-11-20 三项只读任务结果

### 1. loader3 静态分析（capstone.js，7439 条指令）

- 结构：ARM 异常向量表 → CP15/MMU 关闭 → SP=0x13000 → BSS 清零 → 跳到 zboot
- 151 个 PC 相对字面量，命中外设只有：
  `0x70029CF0/CE0/E4/E8/EC/F4`、`0x70002000/2004`、`0x70001F00/1F10`、
  `0x7C0151F0/51F4/5200`，以及低地址 SRAM/DRAM 参数
- **没有任何 SD/MMC/FAT/文件系统代码，也没有 UART 引用**
- 141 个 BL 目标中真正落在 0xC000 内的只有约 11 个函数

→ 「从卡启动」不可能在 loader3 里，只可能在更后面的 Linux 用户态或 Venus 侧 `program`。

### 2. RAM dump 扩展

- 现在覆盖 `0x80000000..0x81140000`（18MB），合并为 `out/ram_full.bin`
- 从 `0x807D3000` 切出 squashfs 镜像（9,826,740 字节）：超级块完全自洽
  （inode/dir/frag/id 四张表的偏移依次递增、bytes_used 与镜像大小一致）
- **但镜像正文用 LZO 解不开**：LZO1X 报 lookbehind 错误，gzip/deflate 也不匹配，
  各种 1–16 字节偏移都试过。熵只有 4.5–7.3，不像加密数据。
  → 可能不是标准 LZO 帧（带长度前缀？），或用了别的压缩器但 superblock 的 comp 字段没改。

### 3. flash 是否被 CPU 映射：否

试了 `0x0`、`0x0800_0000`、`0x1000_0000`、`0x2000_0000`、`0x3000_0000`、
`0x4000_0000`、`0xE000_0000`、`0xFC00_0000`（都加 `0xA800`），
结果既不是 loader3 明文也不是它的密文；`0x0A800` 是擦除态。flash 挂在控制器后面。

## 尚未证实 / 关键未知

- **改了地址之后，数据到底有没有写到新地址？** `storage` 的 size=0，这条实验没写任何数据。
- **flash 里存的是明文还是密文？**
  - H1：更新时解密→写明文。那么整片 flash 都是明文，普通 dump 就能拿到全部固件。
  - H2：更新时只校验、仍写密文，启动时再解密。那么「把 A 解密写到 B」这条思路**根本不成立**，
    因为 B 处放进去的是 A 的密文，启动时会被 B 的 IV/密钥解成乱码。
- **有没有启动时整片/逐分区哈希校验？** 往空洞里写东西是否会导致开不了机，未知。
- **回读通道**：这是整个方案的死穴。用户提到的「DSC→SD 读回来」目前没有细节，
  提供这个思路的群友已离线。

## 为什么回读是前提

如果 H1 成立，普通 flash dump 就已经是全部明文 —— 那么「定向写入」只在
「只能读部分区域、不能整片 dump」的前提下才有意义。没有回读，写了也看不见。
如果 H2 成立，这个方案从原理上就不成立。
