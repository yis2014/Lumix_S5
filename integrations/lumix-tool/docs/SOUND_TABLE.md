## 1. 表项结构

每项 32 字节，按 u32 解读：

| 偏移 | 字段 | 说明 |
|---|---|---|
| +0x00 | id | 音效编号（0..27） |
| +0x04 | 采样地址 | **虚拟地址**，播放时读取 |
| +0x08 | 第二地址 | 辅助缓冲/结束地址，行为未完全确认 |
| +0x0C | 第三地址 | 同上 |
| +0x10 | 第四地址 | 同上 |
| +0x14 | **PCM 字节数** | = 采样点数 × 2。**已实测**：44100 采样必须写 88200 才播完整；按采样数写只会播一半 |
| +0x18 | 配置指针 | 指向该音效的配置结构（半字标志） |
| +0x1C | 标志 | 常见值 1 |

播放路径：`0x86479E40` 附近代码执行 `table + id*32`，读 `+0x18` 指针与半字标志；
`0x86479E5E` 为带 `switch(id)` 的播放函数（id < 0x17 分支）。

## 3. 地址换算

```
物理地址 = 虚拟地址 + 0x80000000
程序内偏移 = 物理地址 - 0x86280000     （program 段起始）
表项地址 = 0x86E35100 + id × 32
```

当前暂存区为 `[0x8F000000, 0x8F800000)`（虚拟 `0x0F000000` 起）。这块 RAM 在电源键热重启后内容保留，所以写入的音效热重启后仍然有效；但也意味着里面会残留之前写入或实验留下的数据（见 §4.1）。中间曾短暂改用 `[0x8B5B0000, 0x8BAD0000)` 的全零区域（提交 e59b596），已改回。

## 4. 替换任意音效的标准流程

1. **准备音频**：44100 Hz、单声道、signed 16-bit LE 的 PCM；建议 ≤ 3 秒
   - 应用内用 Web Audio 解码后重采样，已实现
2. **扫描、分配并检查写入区域**（见 §4.1）：每个半字一次 `0x9C` 写（约 2 ms/次）
   耗时 ≈ 采样点数 × 0.002 秒
3. **改目标表项**：`+4 = 区域物理地址 + 16 − 0x80000000`（PCM 虚拟地址）、`+0x14 = 采样点数 × 2`（**字节数**）
4. **电源键热重启**（不要拔电池），触发对应动作试听

工具（`app/python/s5focus.py`）已支持：

```bash
python s5focus.py status                    # 连接/状态
python s5focus.py dump                      # 导出全部 28 项（JSON）
python s5focus.py apply <pcm> <samples> <region_addr>  # 显式物理地址，写 PCM 并改 ID1
python s5focus.py apply-slot <index> <pcm> <samples> <region_addr>  # 守卫检查后写入任意项
python s5focus.py apply-id <id> <pcm> <samples> <region_addr>  # apply-slot 的兼容别名
python s5focus.py scan [start] [length]      # 只读扫描，默认整个暂存区 0x8F000000–0x8F800000
python s5focus.py restore                   # 恢复原厂 ID1
python s5focus.py restore-id <id> <32字节hex>    # 恢复任意 ID（用 dump 的 hex）
```

> 表项原始值务必先用 `dump` 保存，恢复时用 `restore-id`。

### 4.1 LumixTool 扫描与分配 RAM 区域

**暂存区**：`[0x8F000000, 0x8F800000)`。电源键热重启后这块 RAM 的内容保留（写入的音效因此热重启后仍有效），
所以其中会残留之前写入或实验留下的数据。历史：

1. 最早用固定步长给每项算地址；实机（0x0290）上 #1 的 `0x8F084100` 不是全 `0x55`，旧守卫拒绝写入。
2. 改为先扫描再分配，只往全 `0x55` 的区段写。
3. 提交 e59b596 曾把暂存区换到全零的 `[0x8B5B0000, 0x8BAD0000)`；提交 730faad 又改回 `0x8F`，
   理由是 `0x8F` 区域热重启后保留，而残留的旧数据不代表固件正在使用。

**扫描**：「内存诊断」只用 `0x5C` 读取整个暂存区，每块 1 KiB，按 `free-0x55`（全 0x55）、`zero`（全零）、
`lumixtool`（以有效 `LMXTSLOT` 头开头）、`data`（其它）分类并合并连续块。输出 `PROGRESS <done> <total>` 和一行 JSON；
扫描不发送任何写命令。缓存按机身版本保存在 userData 的 `memory-maps.json`（模拟模式为 `memory-maps-mock.json`）：
`{ scannedAt, bodyVersion, start, length, runs }`。

**当前占用**以声表 `dump` 为准：采样虚拟地址位于暂存区的条目，占用 `[PCM物理地址 − 16, PCM物理地址 + 字节数)`，
其中字节数取自表项 `+0x14`，结束地址向上取整到 1 KiB。

**分配**：写入 `n` 个采样需要 `16 + 2n` 字节，向上取整到 1 KiB：

1. 若该项已有区域容量足够且起点按 1 KiB 对齐，复用同一起点。
2. 否则在扫描结果中**除 `lumixtool` 以外的所有区段**（`free-0x55`、`zero`、`data` 都算可用，`data` 被视为残留数据）
   按地址顺序 first-fit，排除其他项的当前占用，以及本批次之前已分配的空间。
3. 本机身版本无有效缓存时，先进行只读扫描。
4. 批量操作先分配所有项再写入；空间不足时报告需新分配空间、总可用和最大连续可用，整批零写入。

**区域格式**：起点按 1 KiB 对齐，头部和 PCM 的完整范围都在暂存区内（连接设备前校验）。
前 16 字节头：`b"LMXTSLOT"`、小端 u32 索引（0..27）、小端 u32 采样数（1..132300）；PCM 从 `region_addr + 16` 开始。
只改声表 `+4 = region_addr + 16 − 0x80000000` 与 `+0x14 = samples × 2`（**字节数**）。

**写入前的守卫规则**（提交 730faad 起）：读取 `[region_addr, region_addr + 16 + samples × 2)`，
**只有当它以另一个编号的有效 `LMXTSLOT` 头开头时才拒绝**；全 `0x55`、全零、残留数据、同编号的头、无效的头都允许覆盖。
拒绝时返回 `{"ok":false,"error":"region not free","address":"0x8F000000"}`，本项头、PCM 和表项都不写。

> ⚠️ 这比之前「只往全 0x55 写」宽松得多：守卫不再能发现固件正在使用的内存，只能防止 LumixTool 的两个音效互相覆盖。
> 这一取舍依据的是 0x0290 上对 `0x8F` 区域的实测（热重启后保留、残留数据不属于固件）。

被拒绝时，应用把该分配块在缓存中标为 `lumixtool`（那里已有别的音效的头），显示中文错误和重新扫描按钮，停止后续项且不自动重试。
成功写入后也标为 `lumixtool`，保留原扫描时间。批量中其他传输失败也会立即停止并报告成功、失败与未执行编号。

**原厂备份**：连接后，只有采样地址落在固件程序区 `[0x06280000, 0x07280000)` 的表项才被视为原厂并备份（每项只备份一次，按机身版本记录于 userData）。
指向任何暂存区（包括曾短暂使用的 `0x8B5B0000` 区域）的表项都视为已替换。首次连接时已替换但无备份的项只能通过拔电池还原。恢复只改表项，不清除旧 PCM。

### 4.2 固件版本与声表自检（写入闸门）

音效表地址 `0x86E35100`、机身版本字段 `0x863B0000`、暂存区地址都是在机身版本 **0x0290**（v2.9）上实测确定的。其它固件版本在这些地址上可能存放着别的数据，因此后端 `s5focus.py` 在 `apply` / `apply-slot` / `apply-id` / `restore` / `restore-id` 真正写入前都会先读取并检查：

1. **机身版本**必须在白名单 `VERIFIED_BODY_VERSIONS`（目前只有 `0x0290`）中；
2. **整张音效表**看起来必须是音效表：28 项的 `+0` 编号依次为 0..27，`+0x14` PCM 字节数在 `1..0x100000` 之间，`+4` 采样地址位于固件程序区 `[0x06280000, 0x07280000)`、当前暂存区（虚拟 `0x0F000000` 起），或曾短暂使用的 `[0x0B5B0000, 0x0BAD0000)`。

任一条件不满足时返回 `unsupported firmware: ...` 或 `sound table check failed: ...`，不发送任何写命令。`restore-id` 还要求传入的 32 字节是该编号的原厂表项（编号一致、地址在程序区内）。`status` 返回 `verified` 和 `table_problem`，界面据此在未验证的固件上禁用写入和恢复，只开放查看与内存扫描。

验证新的固件版本后，把它加入 `VERIFIED_BODY_VERSIONS`，并在本文档记录对应的地址。

## 5. 已验证 / 已证伪

**验证成功**：把 ID1 的 `+4/+0x14` 指向暂存区的 1 秒两音 PCM，热重启后半按快门，对焦音变成自定义音。

**证伪**：单独改 ID20（参考文档称其为快门音）后，按快门毫无变化。
**补充证据**：把全部 28 项都指向同一 PCM 后，用户反馈「所有音效都变成一样的了」——
说明快门音**确实在这张表里**，只是不是 ID20。

**未确认**：ID20 是否被音频引擎缓存（改了无效），还是它根本不是快门音。

### 6.2 静态分析结论（为什么不能直接从代码里读出常量 ID）

播放链路（全部位于 program 段）：

```
UI/事件层  →  投递音效请求（队列）  →  消费循环 0x864783EA
                                        ├─ 0x864BCFF0  取消息
                                        ├─ 0x86479A40  过滤/检查
                                        └─ 0x8647994C  播放包装函数（r0 = 音效 ID, r1 = 参数）
                                              └─ 0x86479E3C → 0x86479E5E  按 id 查表播放
```

- `0x8647994C` 的唯一调用者是 `0x86478458`，而它从队列消息里**动态读取** ID
  （`ldrb r0,[sp,#5]` / `ldrb r1,[sp,#6]`），所以调用点没有常量 ID
- `0x86F49928` 起有一张 ID 列表（`0x11,0x14,0x15,...,0x22`），属于消费端的白名单/路由表
- 结论：动作与 ID 的对应关系发生在**投递端**（UI 各功能模块），静态追踪需要逐模块逆向；
  用二分法实测更快

### 6.3 二分法定位任意动作的 ID

每轮：改一半 ID → 热重启 → 触发动作 → 听是否变化。28 个 ID 最多 5 轮。

**准备**：先保存原始表（一次即可）

```bash
python s5focus.py dump > sound_table_original.json
```

**第 1 轮**（测 0..13）：

```bash
# 把 0..13 改成自定义 PCM
python s5focus.py apply-id 0  my.pcm 44100
python s5focus.py apply-id 1  my.pcm 44100
...
python s5focus.py apply-id 13 my.pcm 44100
# 14..27 保持原样（若之前改过，用 restore-id + dump 的 hex 恢复）
```

热重启 → 触发目标动作：
- 声音变了 → 目标在 0..13，下一轮测 0..6
- 没变 → 目标在 14..27，下一轮测 14..20

**收敛**：每轮把区间对半，5 轮内定位到单个 ID。

**恢复**：

```bash
python s5focus.py restore-id <id> <dump 里该 id 的 32 字节 hex>
```

## 7. 限制与风险

- **仅 RAM**：拔电池 / 恢复出厂后全部还原；电源键热重启保留
- 写入耗时与采样数成正比（1 秒 = 44100 半字 ≈ 88 秒；3 秒 ≈ 265 秒）
- 部分音效可能被引擎在启动时缓存（ID20 现象），替换后需验证是否真正生效
- 采样长度超过原条目时，需确认引擎不会越界读取（暂未验证）

## 8. 后续实现「全部音效可替换」的建议路线

1. 用二分法补齐 28 个 ID 的触发映射
2. 每个 ID 的原始 32 字节表项、长度上限记录成表
3. 应用里做成「音效列表 + 逐项替换 + 一键恢复」
4. 若要持久化（不拔电池也永久保留），仍需解决固件刷写的启动链验签（当前阻塞项）
