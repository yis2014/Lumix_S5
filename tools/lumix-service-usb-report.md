# Panasonic DC-S5 服务 USB 通信复现报告

日期：2026-11-17　设备：Panasonic DC-S5（`04DA:2370`）　主机：Windows，管理员权限

## 1. 结论

在不使用任何松下官方软件、不安装 Zadig 图形工具的前提下，从零实现了与 DC-S5
服务接口的通信，并完成：

- 厂商自定义接口的驱动绑定（自签名 WinUSB 包）
- 维修/服务协议握手（帧格式、校验、收发时序）
- 区域表查询（`0x3a`）
- 设置区字读取（`0x38` 存储读 / `0x35` 影子读）
- 绝对半字读（`0x9b`）
- 1 KiB 绝对块读（`0x5c`），实际读出 ARM 异常向量表与启动代码

**读出的机身序列号与 Windows 在 PTP/存储模式上报的序列号完全一致**，构成独立交叉验证。

## 2. 设备与描述符（实测）

| 项目 | 值 |
|---|---|
| VID:PID | `04da:2370` |
| 设备类 | `00/00/00` |
| bcdUSB / bcdDevice | `0x0200` / `0x0100` |
| 配置 / 接口 / 备用设置 | 1 / 0 / 0 |
| 接口类 | `ff / a0 / b0`（厂商自定义） |
| 端点 | `01` BULK OUT 512、`82` BULK IN 512、`83` INTERRUPT IN 64（interval 16） |
| bmAttributes | `0xC0`（自供电） |
| 字符串 | iManufacturer="Panasonic"、iProduct="DC-S5"、**iSerialNumber=0** |

同一 USB 口上还观测到该机的其它四种模式（2372 存储 / 2374 与 2382 PTP / 2381 HID），
均带真实序列号；只有 2370 模式不提供序列号。

## 3. 驱动绑定（无需 Zadig）

`E:/desktop/LUMIX/.workbuddy/tools/winusb/`：

1. 手写 `dcs5.inf`（`Include=winusb.inf` / `Needs=WINUSB.NT`，硬件 ID `USB\VID_04DA&PID_2370`）
2. `New-SelfSignedCertificate` 生成代码签名证书，导入 `Root` + `TrustedPublisher`
3. `makecat` 由 `dcs5.cdf` 生成目录文件，`signtool sign /fd sha256 /sm /s My /sha1 <thumb>`
4. `pnputil /add-driver dcs5.inf /install`

结果：设备状态由 `CM_PROB_UNKNOWN`（问题码 28）变为 `OK`，`Service=WINUSB`。

## 4. 协议

### 4.1 事务时序（7 步）

```
1. 控制传输  40 00 0000 0000 0000   (bmRequestType=0x40, bRequest=0, wIndex=0, wLength=0)
2. BULK OUT  0x01  <- 16 字节请求帧
3. 延时 100 ms
4. 控制传输  40 00 0000 0100 0000   (wIndex=1)
5. BULK IN   0x82  -> 1 字节响应类型（必须 0x08）
6. 控制传输  40 00 0000 0100 0000
7. BULK IN   0x82  -> 完整 16 字节帧（含类型字节）
```

**关键点**：厂商请求的 recipient 必须是 **device（`0x40`）**。用 interface（`0x41`）
或 `0xC1`/`0xC2` 一律 STALL，会被误判成"设备不支持厂商请求"。

### 4.2 16 字节帧

```
[0] 类型 0x08
[1] 序号 0x00
[2] 序号反码 0xFF
[3] 操作码
[4..5] 索引 / 地址低半字（小端）
[6] 区域号（仅 0x38 使用）
[7..13] 0
[14] 校验 = sum(bytes[1..13]) & 0xFF
[15] 终止符 0x00
```

成功响应 `[3]=0x36`；错误响应 `[3]=0x01`，`[4..5]` 为错误码（`3` = 越界/参数拒绝）。

### 4.3 字节序（重要）

**数据为 big-endian**：word `0x584A` 解码为 `"XJ"`，不是 `"JX"`。
GM 系列文档按小端记录，直接套用会读出乱序字符串。地址字段则是小端。

### 4.4 操作码

| 码 | 含义 | S5 实测 |
|---|---|---|
| `0x3a` | 区域元数据查询 | 可用，回 `0x3b`，class `0x10`（262 字节） |
| `0x35` | 设置区影子（RAM）字读 | 可用，约 98 字/s，值会随运行变化 |
| `0x38` | 装入选定存储 bank 后读一字 | 可用，约 38 字/s |
| `0x9b` | 绝对半字读（地址在 `[4..7]`） | 可用 |
| `0x5c` | 绝对 1 KiB 块读（1030 字节 class-one 帧） | 可用 |
| `0x34` / `0x4a` / `0x9c` | 写操作 | **未使用** |

## 5. 区域表（`0x3a` 实测）

记录格式：5 字节 = 区域号(u16 LE) + 容量(u16 LE，单位 256 字) + 1 字节保留；`[4]` 为行数。

| 区域 | 容量 |
|---|---|
| `0x10` | 65536 字（128 KiB） |
| `0x11` | 65536 字 |
| `0x21` | 65536 字 |
| `0x22` | 65536 字 |
| `0x30` | 3072 字（6 KiB，仅 `0x35` 可访问） |

其余 9 行为 `0xff` 占位。该表与公开的 GX9（2018）记录逐项一致，说明 S5 使用的是
GX9 一代的服务分发器，而非 GM1/GM5 那一代。

## 6. 验证结果

### 6.1 设备标识（区域 `0x21`）

```
+0x00  XJR2208230009     ← 机身
+0x20  MXD2H43000945     ← 主板
+0x40  X9228190337       ← 传感器
+0x60  WJ2HB002960       ← 镜头
```

`XJR2208230009` 与 Windows 在 PTP/存储模式上报的
`0000000000000000000XJR2208230009` 完全一致。

### 6.2 绝对读（`0x9b`）

```
0x80000000 -> 0x0012
0x80000002 -> 0xEA00
```

合成为 32 位字 `0xEA000012`，即 ARM 指令 `B #0x50`。

### 6.3 块读（`0x5c`）

`0x80000000` 起 1 KiB：

```
12 00 00 EA  05 00 00 EA  04 00 00 EA  09 00 00 EA
```

即 `EA000012 / EA000005 / EA000004 / EA000009`，标准的 ARM 异常向量表
（reset / undef / swi / prefetch abort）。

重复读三次 SHA-256 完全一致：

```
884f12a87751eb291fc2e038cf530caf...
```

已采集：`0x80000000` 起 16 KiB、`0x80004000` 起 128 KiB
（后者为压缩/高熵数据，SHA-256 `4229fa407517c06b...`）。

## 7. 边界与风险

- 第 1–9 章全部为只读操作，未修改相机内任何数据。写能力另见第 11 章：唯一一次写入
  发生在已验证为 `0xff` 填充的 1 KiB 块内，且已逐字节复原（块摘要回到基线）。
- 绝对地址读依赖目标地址已映射。**旧型号地址 `0x40000000` 在 GX9 上曾导致死机**，
  本次未尝试；S5 的完整地址映射仍未确定。
- 盲发未识别数据会让设备 EP0 全面 STALL；`pnputil /restart-device` 会使设备暂时
  脱离总线。两种情况均需重新上电并重进维修模式。
- `0x35` 读到的是 RAM 影子，内容随运行变化，不可作为稳定备份来源。

## 9. 对"跳过签名所以不需要私钥"这一说法的核对

公开记录（`flickering-star/lumix-firmware-research`）自身给出的证据是：

- GM1 的正常更新路径存在 **ECDSA P-256 目录签名校验**，已用官方固件独立验证。
- 该文档原话：解密密钥"does not provide the signing capability needed to change
  this directory"。
- 配套程序"recover the required key **from the connected service camera**"。

也就是说，通过服务 USB 取得的是**相机内存中的对称解密密钥**，不是松下的签名私钥。
签名验证只需公钥，只有签发才需私钥，因此"不需要私钥"成立但无信息量；真正稀缺的是
机内解密密钥，而取得它的唯一路径正是服务 USB 的内存读取能力。这与本次实测一致：
读通道一旦打通，能拿到的是机内数据（序列号、代码、密钥），而不是签名能力。

## A.4 关键判读

**一、载荷是加密的，不能逐字节比对。** 48 个组件中除占位项外，熵一律 8.000，可打印
字节比例 38.3%——这恰好是随机分布的理论值（98/256）。所以「拿官方固件和相机内存
对字节」这条路在原理上就不通。

**二、摘要给了一条正规的比对通道。** 既然 `+0x1c` 是明文摘要，正确做法不是比字节，
而是：完整读出一个组件 → 算 SHA-256 → 比摘要。这与 GM1 那次「读出的内容与官方
固件中的摘要匹配」是同一个方法，只是这次摘要是我们自己从容器里取出来的。

**三、实测比对未通过，且原因值得记录。** `0x80000000` 起 4 KiB 的实测
SHA-256 = `8cc3a194d6403e05…`（内容是 8 条 ARM 异常向量 `EA000012/05/04/09/0A/0B/0B/05`），
与 `loader1` 的官方摘要 `e009d688fb152a70…` 不符。两种解释，目前无法区分：
装载基址不是 `0x80000000`，或存储的明文与内存镜像之间还有一层解压/重定位。
每个组件同时带 32 字节与 16 字节两个摘要，也支持「两段式完整性」的判断。

**四、6 个组件在官方固件里是空的，这一条最有用。** `storage`(0)、`history`(`0x00`)、
`lens_hist`(`0x00`)、`fileinfo`(`0xFF`)、`ninsho_db`(`0x00`)、`wifi_info`(`0x00`)、
`menu_save`(`0xFF`) 的正文分别是纯填充。含义很明确：**这些区域装的是本机独有数据
（快门计数、镜头历史、文件信息、认证库、Wi-Fi 配置、菜单状态），固件更新不会写它们，
更新包也不含它们。** 一旦被覆盖，没有任何官方途径可以恢复。

反过来，`eep_ow_a/b`、`eep_adj`、`eep_fix`、`eep_act_a/b` 在更新包里是**有内容的**，
即出厂标定默认值。这类区域即使写坏，理论上可被再次更新覆盖回默认值——但仍然会丢掉
本机标定，不建议作为试验田。

# 附录 B：写能力验证（`0x9c` 半字写）

## B.1 帧格式

16 字节，与读操作同一套外壳，区别只在 `op=0x9c` 且第 4–9 字节承载地址与数据：

```
08 00 FF 9C <addr:4B LE> <data:2B LE> 00 00 00 00 <sum> 00
```

成功 ACK 为 `08 00 FF 01 00×10 00 00`。注意：写操作的 ACK 状态字节是 `0x01`，
与读操作的 `0x36` 不同；`0x01` 后面跟全零才是成功，跟 `03` 则是参数被拒。

## B.2 实验（目标 `0x80009C00`）

目标选在 `0x800098AC` 起约 10 KiB 的纯 `0xff` 填充区内，其所在 1 KiB 块整块皆为
`0xff`，因此「改了多少字节」可以直接从块摘要差异读出。

| 步骤 | 写入 | ACK | 读回字 | 1 KiB 块 SHA-256 | 差异字节 |
|---|---|---|---|---|---|
| 基线 | — | — | `0xFFFF` | `5f4ecdb7b71c3e40…` | — |
| 同值写 | `0xFFFF` | 成功 | `0xFFFF` | `5f4ecdb7b71c3e40…` | 0 |
| 改值写 | `0xA55A` | 成功 | `0xA55A` | `b905911884a66840…` | **2**（偏移 `0x0`,`0x1`） |
| 复原写 | `0xFFFF` | 成功 | `0xFFFF` | `5f4ecdb7b71c3e40…` | 0 |

三次写入的原始帧：

```
0800FF9C009C0080FFFF00000000B500
0800FF9C009C00805AA500000000B600
0800FF9C009C0080FFFF00000000B500
```

## B.3 这个结果说明什么、不说明什么

**说明**：`0x9c` 在 S5 上是一个可用的半字写原语，写后读回一致，且只影响目标 2 字节，
没有发生扇区擦除——这是 RAM 存储语义，不是 flash 编程语义。

**不说明**：它不是一个 flash 写入器。没有任何证据表明能改写固件区、能改用户设置、
或能安装修改过的镜像。GX9 的公开记录同样只声明到「RAM writer」为止。

（证据文件：`write_test_evidence.json`；脚本：`lumix_write_test.py`）

# 附录 C：内存全貌、密钥搜索与容器布局修正（2026-11-17 晚）

## C.1 这台机器的内存只有 46 MiB，且已被完整 dump

从残留的内核启动日志（`0x806ab9d0`）读到：

```
On node 0 totalpages: 11776
Normal zone: 92 pages used for memmap
Normal zone: 11776 pages, LIFO batch:1
Built 1 zonelists in Zone order, mobility grouping on.  Total pages: 11684
Kernel command line: root=/dev/mtdblock0 slram=slram0,0x83100000,+0x00300000,...
```

11776 × 4 KiB = **46.0 MiB**，与我们 dump 的 `0x80000000`–`0x82e00000` 恰好等长。
**结论：内核管理的物理内存已经 100% 抓全，不存在"再往上多读一点"的空间。**

两条附带情报：

- `root=/dev/mtdblock0` —— 根文件系统在闪存上，经 MTD 访问，**不映射进内存**。
  因此 `usbd`、`usb_mem.ko`、更新程序这些二进制**无法通过内存读原语取得**。
- `slram=slram0,0x83100000,+0x00300000` —— 另有一块 **3 MiB 保留内存位于 `0x83100000`**，
  在内核管理范围之外，也就在我们 dump 之外。这块尚未读取。

## C.2 密钥搜索：46 MiB × 2 切片 × 2 轮数，全部零命中

判据不再依赖 IV。CBC 下 `P1 = D(C1) ⊕ C0` 与 IV 无关，而 `dtb` 组件明文第 16–31 字节
由 FDT 规范钉死（取自 RAM 中实际加载的 DTB）：

```
00000028 00000011 00000010 00000000     off_rsv=0x28, version=17, last_comp=16, cpuid=0
```

用后 8 字节作判据，随机命中率 2^-64。判据本身做过自检：构造密钥 → 精确单点命中、
200 万窗口零误报。

| 密文起点 | 轮数 | 覆盖窗口 | 候选 |
|---|---|---|---|
| `off+0x200` | 5（松下变体） | 48.2 M | 0 |
| `off+0x200` | 10（标准 AES-128） | 42.0 M（未含最后一段） | 0 |
| `off` | 5 | 48.2 M | 0 |
| `off` | 10 | 进行中 | — |

**这在统计上是强结论**：若密钥以明文 16 字节（或密钥调度表的前 16 字节）存在于内存任一
字节偏移上，四组里至少有一组会命中。零命中意味着：**该密钥在当前运行状态下不以明文形式
驻留于内核管理的 46 MiB 内存中**。

## C.3 容器布局修正：0x200 头区不参与明文哈希

先前记录里"正文在 `off+0x200` 且长度等于 size"是错的：`off+size` 恰等于下一项 `off`，
所以条目总长就是 `size`，其中前 `0x200` 是**不参与哈希的头区**，密文长度为 `size-0x200`。

证据：`history` 的 `h1` 精确等于 `SHA256(0x00 × 0x40000)`，而该条目里 508 个非零字节
**全部落在前 0x200 内**。占位项（`history`/`lens_hist`/`fileinfo`/`ninsho_db`/`wifi_info`/
`menu_save`）的头区有内容、载荷是纯填充。

`loader1` 是特例：头区只有 28 个非零字节（`45c07d28…` 16 字节 + 12 字节），其余全零。

## C.4 USB 模式不是常量，而是脚本参数

内存中完整取到了 `/usr/pvc/etc/init.d/` 的一组脚本，其中 `usb_gadget.sh` 是 USB 身份的
唯一建立者：

```sh
idVendor=0x04DA
idProduct=0x2372            # 默认：大容量存储
gadgetdir=/sys/kernel/config/usb_gadget/g1
usb_mem_module_name=usb_mem
venus_usb_module_name=dwc3-pvc03v
...
'start') . $2 ; start_device ;;      # ← 全部参数来自外部配置文件
```

三条推论：

1. **PID 是配置文件的字段，不是固件常量。** `0x2372` 只是脚本里的默认值。
2. `UseFFS=1` 时会 `insmod usb_mem.ko` 并挂载 **functionfs**；配套的 `usbdevstart` 脚本
   执行 `./usbd &`。也就是说服务 USB 的**服务端是一个用户态守护进程 `usbd`**。
3. 在 46 MiB 里检索 `2370`、`usb_mem.ko`、`/usr/pvc/bin/usbd` 均为 **0 次**，`0x2370`
   的字面量命中经逐处核查全部是内核段表/kallsyms 的巧合。**说明建立 2370 身份的那段代码
   当时不在内存里** —— 与"根文件系统在 MTD 上、二进制按需换入"一致。

## C.5 路径可行性（依据以上实测）

| 路径 | 价值 | 成本 | 风险 | 前置条件 |
|---|---|---|---|---|
| 读 `0x83100000` +3 MiB 保留内存 | 中 | ~40 s | 撞未映射页则冻机，可恢复 | 无 |
| 更新过程中 dump 全 RAM（46 MiB） | **高** | ~10 min | 会真实写闪存 | 需要你在场、电量充足 |
| 从闪存取 `usbd`/更新程序 | 高 | 未知 | 无（只读），但缺 flash 寻址 | 需先找到 MTD 映射途径 |
| 继续在 RAM 找密钥 | 低 | 低 | 无 | 已被 C.2 基本排除 |
| 用 `0x9c` 改策略值 | 极低 | 低 | 每次冻机需你手动恢复 | 前提（持久化）不成立 |

**C.2 与 C.4 合起来改变了结论的方向**：密钥不在内存、更新程序不在内存，两件事都指向
同一个动作 —— **必须让更新流程真正跑起来，在它运行的那一刻抓内存**。那时解密密钥、
接受策略、以及 `usbd` 的完整代码都会同时在内存里，46 MiB 一次就能抓全。

# 附录 D：执行方案（2026-11-17 夜）——让更新流程跑起来，在它运行的那一刻抓内存

## D.1 本轮新增的两个硬结论

**一、46 MiB 里确实没有任何 AES 密钥调度表 —— 这次是用通过标准的检测器重新确认的。**
`keywatch.py` 的检测器对 FIPS-197 附录 A 的 128/192/256 三组官方向量全部命中，
对 500 个随机 1 KiB 块零误报，然后以 1 KiB 步长重扫全部 46 MiB（8 秒）：
**标准密钥调度命中 0 处**。C.2 的结论由此从"IV 无关判据没命中"升级为"调度表也不存在"。

**二、内核里有完整可用的 AES，但更新程序不在内存。**
`ram_tail.bin` 中检索到 S 盒/逆 S 盒成对出现，位置：

| 地址 | 内容 |
|---|---|
| `0x81BB112E` / `0x81BBAF00` 附近 | S 盒、逆 S 盒（另一份拷贝） |
| `0x81BCAF00` | S 盒，后接逆 S 盒 `0x81BCBA80` |
| `0x81BCB…` 字符串 | `AES for ARMv4, CRYPTOGAMS by <appro@openssl.org>`、`Bit-sliced AES for NEON` |

也就是说 **CPU 随时能解密，缺的只是"让谁来调用它"**。这与 C.4 完全咬合：负责解密的
用户态程序（`usbd` / 更新程序）是按需从 MTD 换入的，静止时不在 RAM 里。

**结论：只剩下一个动作有意义 —— 触发更新，让解密真的发生，在它发生的那几秒里抓内存。**

## D.2 触发链的设计：只改明文头里的"文件版本"，正文一个字节不动

容器头（512 字节明文）里版本字段是 **BCD**：`0x0290` = 2.90，`0x0280` = 2.80。
同一字段出现两次（外层头 `0x1c`，内嵌头副本 `0x2bc`），另有"最低可用版本"在
`0x1e` / `0x2be`。

关键性质：**`0x40` 的 CRC32 只覆盖 `0x200..文件尾`**（已实测，两个版本都吻合）。
所以 `0x1c` 在覆盖范围之外 —— 改它不动 CRC；`0x2bc` 在范围内 —— 改它必须重算 CRC，
而 CRC32 不带密钥，我们能自己重算。

`mktrigger.py` 生成四个候选，全部已校验 CRC 一致，且与 `S5___V29.bin` 的差异字节数
精确到个位（见下表最后一列）：

| 候选 | 目录 | 改动 | 差异字节 |
|---|---|---|---|
| `v28` | `trig/v28/` | 无（原厂 V2.8，一个字节没碰） | — |
| `patch_outer` | `trig/patch_outer/` | 仅 `0x1c` ← `0x0300` | 2 |
| `patch_full` | `trig/patch_full/` | `0x1c`、`0x2bc` ← `0x0300`，重算 CRC | 8 |
| `patch_badmusic` | `trig/patch_badmusic/` | 同上 + 翻转 `music` 密文一个字节 | 9 |

**故意不动 `0x1e`/`0x2be`**：若它真是"最低要求版本"，改成 3.00 会让本机 2.90 把自己拦掉。

### 为什么主用候选是"装不上的那一个"

`patch_full` 是"版本抬高、内容原厂"——如果相机接受，它会**一路装完并自动重启**。
而重启会把 DRAM 重新初始化，我们要找的一切当场蒸发。**成功的更新恰恰是最坏的结果。**

所以真正主用的是 `patch_badmusic`：版本抬到 3.00，同时把 `music` 组件密文的第一个块
翻一个字节（`0x1ea2600`，`0xfb -> 0x04`），CRC 随之重算。相机看到的现象是
"文件很新 → 开始解密 → `music` 的 SHA-256 对不上 → 更新中止"。我们要的就是这个中止：

- **解密确实发生了** → 密钥调度进了 RAM；
- **更新中止，相机不重启** → 内存原封不动，可以从容抓；
- 写坏的是 `music`（幻灯片背景音），不是 `loader*`/`program`/`rootfs` 这些一错就变砖的组件；
- 即使它"先写后校验"，写进去的其余部分与原机内容逐字节相同，等于什么都没变。

三个候选的正文都是原厂数据，48 个组件的 SHA-256 全部对得上（`music` 那个是故意破坏的）。

## D.5 执行顺序（每一步都有"停"的判据）

**第 0 步 · 准备（不碰相机）**
SD 卡在相机里格式化一次（FAT32），确认剩余 ≥ 120 MB；电池满电，另备一块；不要用 USB 供电。

**第 1 步 · 基线 + 测速（只读，零风险）**
相机按平时的方式连电脑（`2372`），确认 `04DA:2370` 在。

```
python .workbuddy/tools/keywatch.py --mkbase
python .workbuddy/tools/bench_read.py --n 128
```

测速结果决定第 4 步能扫多快。8 ms/块 = 128 KiB/s = 46 MiB 需 6.3 min；
若能压到 2 ms/块，同样一遍只要 1.6 min。

**第 2 步 · "必拒"演练（零风险）**
把 `S5m2_V37.bin` 拷到 SD 根目录 → 插卡 → 开机进更新界面。
全程跑 `python .workbuddy/tools/keywatch.py --watch watch_reject --delay 0`。
看点：更新界面出现的那几十秒里 `2370` 是否还在（`keywatch` 会打印"设备不在…重试"）。
**若这几十秒通道就断了，后面所有"边更新边抓"的设想全部作废**，只能改成"更新结束后立刻 `--snap`"。

这一步真正要回答的是本轮**最大的未知**：**"更新界面"与"USB 设备身份"是不是互斥的**。
按松下机身的一般行为，插着 USB 开机就进"PC 连接"界面、菜单不可用，而版本升级又必须在
菜单/开机键路径里启动 —— 两者很可能不能同时存在。三种可能：

| 观测 | 含义 | 后续 |
|---|---|---|
| 插着 USB 也能进更新界面，且 `2370` 一直活着 | 最理想 | 第 3、4 步按原计划走 |
| 能进更新界面但 `2370` 消失 | 半理想 | 只能靠中止后的 `--snap`（见下） |
| 插着 USB 根本进不了更新界面 | 需要拔线 | 中止后**先别关机**，立刻插线，看 `2370` 是否回来并抢在自动关机前抓 |

即便走到第三种，也还有余地：Linux 重新初始化 DRAM 控制器通常不会擦除颗粒内容，一次
热重启之后旧 RAM 里仍有大量残留。所以"更新结束后抓"从来不是废动作，只是成功率不如
"更新进行中抓"。

**第 3 步 · 逐级触发**

| 顺序 | 用哪个 | 若被拒（提示版本相同/过旧/文件错误） | 若被接受 |
|---|---|---|---|
| 3a | `trig/v28`（原厂 V2.8，零改动） | 说明有降级门限 → 进 3b | 真实降级开始 → 立刻进第 4 步 |
| 3b | `trig/patch_badmusic`（**主用**） | 进 3c；若提示是"文件错误"而非"版本"，说明校验在解密前 | 解密开跑，随后校验失败中止 → 进第 4 步 |
| 3c | `trig/patch_outer` | 说明校验不只看外层版本 → 进 3d | 同 3a |
| 3d | `trig/patch_full` | 头部存在我们看不见的完整性校验，且它在解密之前 → 本路到头 | 同 3a |

3b 之后**不要急着换文件**：更新中止的那一刻，相机通常停在"更新失败，请关机"的界面。
**先别关机/别断电**，立刻做第 4 步的 `--snap`。


**第 4 步 · 抓取（成败在此）**
更新一开始（进度条出现）就 `keywatch --watch` 已经在跑。命中会当场打印
`*** AES-128 密钥调度 @ 0x81xxxxxx key=...` 并把该块落盘。
更新结束后**先别断电**，立刻：

```
python .workbuddy/tools/keywatch.py --snap after_update.bin
```

理由是**余温**：更新程序退出后，它用过的堆不一定马上被覆盖，密钥调度很可能还躺在
freed heap 里。抓全 46 MiB 再慢慢分析，比在进度条那几分钟里抢时间靠谱得多。

**第 5 步 · 收尾**
用 `panasonic_aes.py` / `verify_key.py` 拿候选密钥去解 `S5___V29.bin` 的 `dtb` 组件，
与组件表里的 SHA-256 比对。对上 = 整条链打通。

## D.6 要说清楚的风险

1. **真实写闪存**。3a/3b 一旦被接受，就是真的在改 flash。中途断电/拔线 → 变砖概率不低。
   官方唯一恢复途径是再来一次更新；bootloader 若被写坏就没有第二次。这也是为什么坏字节
   要放在 `music`（背景音轨）而不是 `loader1`/`loader2`——后者写坏就再也起不来了。
2. **`--snap` 与 `--watch` 都是只读**，不写相机，风险仅在"读得太猛可能让更新变慢"。
3. **`0x9c` 写通道本轮完全不用**。B 节那次 2 字节回滚实验已经够证明能力，没必要再动。
4. 更新期间**不要碰 USB 线**。若 `keywatch` 报"设备不在"，那是正常的（更新程序可能自己
   重置了 gadget），让它自己重试，别去拔插。

| 私有层 | `/usr/pvc/{bin,lib}`：`nwa`、`libpvc.so`、`libicc.so`、`libicsm.so`、`libnetutil.so` |

`libpvc.so` 直接 `open("/dev/mem")` 后 mmap —— 这与我们那个"绝对地址读"原语的行为完全一致。

## E.3 启动链（脚本原文）

```
rcS → 依序遍历 /etc/init.d/S??
S02-mount : mount -t proc/sysfs, mount -a, 再把 tmpfs 盖到 /usr/pvc/etc
```

`usbdevstart` 明确写着 `./usbd &`，而 **`usbd` 不在 rootfs1 里**（`/usr/pvc/bin` 只有 `nwa`）。
更新程序同样不在。这与 C.1 的结论一致：它们属于 rootfs2，按需换入。

## E.4 rootfs2 在内存里只留下了"碎片"

全内存搜 `hsqs` 共 6 处，只有一个通过超级块合法性校验：

| 地址 | 结论 |
|---|---|
| `0x807d3000` | squashfs 4.0，437 inode，9.4 MiB，LZO —— rootfs2 |
| `0x8030c3e0` / `0x8030c9e8` | 版本字段乱码，假阳性 |
| `0x8220d4f5` / `0x829fa838` / `0x82b95838` | 同上 |

但它**无法重建**：该镜像的 inode 表在 `0x958626`、目录表在 `0x95bef2`，按偏移取出来是
ARM 指令和别的数据，不是 squashfs 元数据块。原因是 rootfs2 走的是**页缓存**（4 KiB 物理页
各自分配），不是 slram 那样的线性映射，所以文件在物理地址上不连续。**只能靠运气捡到页，
不能整体恢复。**

## E.5 但它的目录结构留下来了

`0x8064d600`–`0x8066c200` 是内核 dentry 缓存，里面是 rootfs2 的完整文件清单，含
`/mnt/rfs2/usr/pvc/{bin,lib}`、`cam.fcgi`、`menuxml/`、`lib/modules/3.18.18/`、
MT6630 WiFi 固件等。另有 203 个 ARM ELF 文件头散布在内存各处——都是被按需换入的
文件页，头在、后续页不保证相邻。

## E.6 一个直接可用的旁证

Windows 侧当前枚举到的设备是 `USB\VID_04DA&PID_2370`，**不是** `2372`，且没有导出任何
大容量存储卷。也就是说：相机现在这套 gadget 配置把 SD 卡留在了相机自己手里。这正是
"在更新流程运行时抓内存"能成立的前提——sd 卡不会被 USB 抢走。

## E.7 空闲噪声基线（决定判据）

对同一台机器连跑两轮全量差分（`keywatch --watch`，1 KiB 粒度）：

```

```

差分信号不会被噪声淹没。

# 附录 G：区域参数（`area`）与地址解码实测——路由 A 收口

本附录回答一个此前悬着的问题：协议里的 `area` 字节能否用来读取 MLC NAND 上的
`program`，从而绕开"让更新流程跑起来"这一前提。**结论是不能**，但过程中确认了
若干此前只有推断的结构，并纠正了两处错误。

## G.1 `area` 是参数/EEP 分区选择器，不覆盖固件

`0x3a` 区域表声明 5 个有效区，实测穷举 `area = 0x00..0xFF`（256 个值 × 2 个操作码）：

| 操作码 | 应答的 area |
|---|---|
| `0x35` | 全部 256 个（含表外）——**假应答**，见 G.3 |
| `0x38` | 仅 `0x10`、`0x11`、`0x21`、`0x22` |

**表外无隐藏区。** `0x38` 对 `0x00`–`0x0F`、`0x12`–`0x20`、`0x23`–`0xFF` 一律回
错误码 3，说明分发器按白名单校验，不存在"未列出的固件通道"。

四个有效区各 65536 字 = **128 KiB**，而 `program` 是 15.9 MiB，相差两个数量级。

**纠正 G-1**：附录 E 按容量把 area 对应到 `eep_ow_a/b` 与 `eep_adj/fix`，这是
**容量巧合而非真实映射**。实测 `0x38` 读 area `0x10`/`0x11`/`0x22` 前 8 字全为
`0x0000`，而容器目录里 `eep_ow_a`/`eep_ow_b` 的明文 SHA-256 是
`6c4be51bd4c8fb00…`（非空）。两者不一致，故映射不成立。

**纠正 G-2**：正文第 5 节写「`0x30` 仅 `0x35` 可访问」。实为**越界**：当时抓包用
`idx = 0x3F80`（16256）> 3072，两个操作码都回错误码 3。与 opcode 无关。

## G.2 `0x38` 的索引只有 16 位

用 `idx ∈ {0, 1, 0x10000, 0x10001, 0x20000}` 实测：`0x38` 与 `0x38` 在 `0x0000`
和 `0x10000` 处返回**完全相同**的值，`0x0001` 与 `0x10001` 亦然 ⇒ 高位被截断，
索引宽度 16 位。因此每个区上限就是 128 KiB，不存在"大索引扩展"。

## G.3 `0x35` 对无效 area 返回的是计时器，不是内存

表外 area 的 `0x35` 全部回 `status = 0x36`（成功），但值是**随时间单调递增的小整数**：
连续三读 `0x1416 → 0x1418 → 0x1419`。同一 (area, idx) 的 `0x38` 则稳定返回
`0x0000`。因此 `0x35` 在参数无效时把内部计时器留在应答缓冲里，**不能当作"该区存在"的证据**。
两个操作码的差值也说明：`0x38` 读实际存储，`0x35` 读影子副本。

`0x38` 读 area `0x21` 前 16 字得到 `58 4A 52 32 32 30 38 32 33 30 30 30 39 …`，
即 ASCII **`XJR2208230009`**，与 PTP 上报的机身号逐字符一致 ⇒ area 通路读的是
真实持久数据，工具链可信。

## G.4 选中 area 不改变绝对地址窗口

依次用 `0x38` 选中 `0x10`/`0x11`/`0x21`/`0x22`，再重读 DRAM 见证块
`0x80100000` 与半字 `0x80000000`：**四个区的结果全部与基线逐字节相同**
（`sha256 = e362d9c0c6b1`）。故 bank 切换不影响 `0x5c`/`0x9b` 的地址解码。

## G.5 绝对地址空间：只有 DRAM，没有 flash 窗口

对基准 `0x80000000` 逐位翻转（`addr ^ (1<<n)`，n = 0..31）并用 `0x5c` 读 1 KiB：

- **只有 bit31 被忽略**：`0x00000000` 与 `0x80000000` 返回同一块（`sha 884f12a87751`）；
  `0x10000000` ≡ `0x90000000`；`0x20000000` ≡ `0xA0000000`。
- **其余 30 位全部有效定址**：bit0–bit4 读出的是基准块按 1/2/4/8/16 **字节平移**的内容，
  这正是真实内存读的特征，可排除"返回固定伪数据"。
- 已知坐标全部复现：`0x88000000` = 浮点参数表（`0000803f` ×3 + `cdcc4c3d`）、
  `0x90000000` = `CDNN`、`0x80200000` = 递增字节图案、`0x40000000` = 全零。

**没有任何地址落在 flash/NAND 上**：全程无 `hsqs`/`UBI#`/`uImage`/`UPD\0` 等固件魔数。

**纠正 G-3**：附录 F 称「`0xC0000000` 处处有结构化数据 ⇒ SoC ≥ 1 GiB DRAM」。
现已证明若 bit31 被忽略，`0xC0000000` 应等价于全零的 `0x40000000`，实测却返回
另一份稳定数据 ⇒ 该地址的行为与"bit31 一律忽略"模型冲突，**不能作为 DRAM 容量的证据**。
DRAM 容量的独立结论需另行验证。

## G.6 副作用（重要，操作约束）

**读未映射的 `0x9b` 地址会让相机的 USB 服务端复位并重新枚举**：扫到 `0x60000000`
后设备从总线消失，`libusb` 报 `device not found`，而 Windows PnP 仍显示
`Status: OK`、实例 ID 不变；数秒后自动恢复，数据无损。`0x5c` 对同类地址则**容忍**
（直接返回全零）。

由此定下操作约束：**地址空间扫描只能用 `0x5c`，禁止用 `0x9b` 扫未知区域。**

## G.7 新工具

| 工具 | 作用 |
|---|---|
| `area_probe.py` | `map` `map5c` `table` `areas` `alias` `switch` `index32` `blk` `all`；只发 `0x3a/0x35/0x38/0x9b/0x5c`，代码内不含写操作码 |
| `addr_decode.py` | `bits`（逐位翻转求解码）、`probe`（3 次重复 + 前后对照判陈旧）、`scan`（区间扫描带对照） |

`0x9b` 与 `0x3a`/`0x38` 的帧构造均与历史抓包**逐字节一致**后才投入使用。

**未做全操作码扫描**：未知码可能含写操作（已知写码 `0x9c`/`0x34`/`0x4a`），
对 flash 的风险不可控，故只扫 `area` 这个已知只读操作的参数。

# 附录 H：服务分发器不在 Linux 里——架构定论（本轮实测）

本轮目标是对齐 GM1/GM5 的方法论（"用相机端命令处理代码补齐命令表"），在 S5 上
寻找等价物。结论是**找不到，因为它不存在于主 Linux 中**，但过程中确定了完整的
服务通路架构、精确的内存映射，并确认了页缓存里的 program 分区内容。

## H.1 请求帧从未出现在 Linux 内存中（自指扫描）

新工具 `selffind.py` 利用协议的自指性质：我们发出的每个 0x5c 请求帧
（`01 00 FF 5C | X | X+1024 | …`）必然躺在处理方的接收缓冲里；扫描到缓冲区
所在块时，返回数据中会出现"嵌入地址等于自身地址"的帧。该扫描对**任意**
持有当前请求帧的内存都有效，与页对齐无关。

实测结果：**全 Linux 受管窗口（0x80000000–0x83100000，47104+3072 块）零命中**，
高段 0x83E00000–0x85000000 亦零命中。若分发器是内核模块或用户态进程，
其 DMA/堆栈缓冲必在受管区——因此**分发器不在主 Linux 中**。

## H.2 `usbd` 进程不存在

- 全 46 MiB 中无 `usbd\x00\x00…` 形态的 task_struct comm 字段；
- dentry 缓存（见 H.4）的 444 个文件名中**没有 `usbd`**（此前的"usbd"命中全部
  是 `usbdevstart` 的子串或脚本内容 `./usbd&`）；
- `usbdevstart` 脚本虽写了 `./usbd&`，但该二进制从未被 exec。

**纠正**：此前"usbd 正在运行、我们的每个请求都是它在处理"的表述不成立。

## H.3 服务通路架构

```
USB 线 ── dwc3@0x7C200000 (panasonic,pvc03v-dwc3)
              │  usb_mem（专用内存池，不在 DRAM 受管区）
              ▼
        独立处理器/固件 ── 总线主设备 ──> 可读全部 DRAM（bit31 屏蔽后 31 位空间）
              │                     └─> 0x9b 读未映射地址会使其复位重枚举（自愈）
              │  icc0..icc15 / icsm（片间通信，Linux 侧驱动 cpu_iccdrv.ko/cpu_icsmdrv.ko）
              ▼
        主 Linux（0x80200000–0x83100000，11776 页）
```

证据链：DTB 节点 `usb@7C100000`/`dwc3@7C200000`；`/dev` 下存在 `usb_mem`、
`icc0`–`icc15` 设备节点；rootfs1 有 `cpu_iccdrv.ko`/`cpu_icsmdrv.ko`/`pvc_eepromdrv.ko`；
页缓存中出现一份**以 0x41000000 为基址的 ET_DYN 预链接副本**（rootfs1 中同名模块
为 ET_REL），DTB cpus 节点带 `cpu-offset`——存在第二执行环境（AMP 分域或协处理器侧）。

## H.4 精确内存映射（运行时 DTB 实测）

- bootargs：`root=/dev/mtdblock0 slram=slram0,0x83100000,+0x00300000,slram1,0x83400000,+0x00A00000 console=ttyAMA,115200`
- `memory@80200000` reg = `0x80200000 + 0x2F00000` → **主 Linux 受管区
  [0x80200000, 0x83100000]**，与 slram0 首地址精确相接（此前"46 MiB"的说法
  是近似值，且漏扫过 0x82E00000–0x83100000 最后 3 MiB，本轮已补扫）。
- MMIO：中断控制器 0x70001000、timer 0x7F02A000、UART 0x7F05xxxx、
  SDIO 0x7C3xxxxx、USB 0x7C100000/0x7C200000（bit31=0，在 0x5c 可读范围内）。

## H.5 页缓存里有 program 分区内容（可间接读取 program）

- 0x81c2c000 起的解压块含 `usb_gadget.sh`、网络初始化脚本等，其内容
  **在 rootfs1 与 rootfs2 中均不存在**（逐字节检索验证）→ 来自 program 分区
  （squashfs 块缓存，kmalloc 缓冲，故 0x81c142f4 的 ELF 头出现在页中间）；
- dentry 缓存（0x82bae000 / 0x806c0000 两份副本）给出 `/usr/pvc` 文件清单，
  计 444 个名字，含 `netstart`、`netdevstart`、`wifidevstart`、`btdevstart`、
  `mediastart`、`cam.fcgi`、`strace`、`openssl`、`lighttpd` 等；
  **无 `usbd`、无 `overnat`**（后者仅在更新时被 psm execlp，从未运行）；
- `/dev` 节点清单：`mtd0 mtd2 mtd3 mtd10 mtdblock0 mtdblock1 mtdblock2 mtdblock3
  nvmd pvc_eeprom icc0..icc15 usb_mem ttyGS stpbt stpwmt ttyAMA`。

## H.6 与 GM1/GM5 方法论的对照

| 环节 | GM1/GM5（公开记录） | 本机 S5（本轮实测） |

# 附录 I：签名机制与"程序分区可读性"的最终裁定（本轮）

本轮把上一轮遗留的三条线索全部做完，得到两个**否定结论**和一处**必须撤回的错误**。

## I.1 撤回：页缓存里没有 program 分区的内容

上一轮（附录 H.5）称"`0x81c2c000` 起的脚本来自 program 分区，其内容在 rootfs1/rootfs2
中均不存在"。**该结论作废**，原因是方法错误：当时是拿**解压后的块**去检索
`rootfs2_full.img`（**压缩**镜像），即使该块属于 rootfs2 也必然检索不到。

用**解包后**的目录重做检索：`0x81c2c000` 前 256 字节精确命中
`rootfs_ext/etc/init.d/mount` 与 `rootfs_ext/etc/init.d/S02-mount`，即 **rootfs1**。
故该处是 rootfs1 的普通页缓存，与 program 无关。

## I.2 program 分区未被挂载（三条独立证据）

1. `fstab` 只有 tmpfs/devpts/run 四项，没有 program；`netstart` 只挂
   `mtdblock1 → /mnt/rfs2`；`init.d/mount` 只做 `mount -a` + tmpfs 覆盖 `/usr/pvc/etc`。
2. 全 49 MiB 内存中**只有一个自洽的 squashfs 超级块**（`0x807d3000`）：inodes=437、
   bytes_used=`0x95f1b4`、root_inode=`0x200218a8`，与本地 `rootfs2_full.img`
   **逐字段一致** ⇒ 是 rootfs2 的，不存在第三个文件系统。
3. `/usr/pvc` 的真实来源是 rootfs2：`netstart` 里 `cd /usr/pvc/bin; ./net&`，
   而 `net`（5552 B）只存在于 `rfs2/usr/pvc/bin/`；rootfs1 的 `/usr/pvc/bin` 仅 `nwa`。

**结论**：正常运行时 program 分区既不挂载也不被读取；`usbd`、`overnat` 两个二进制
在**两个 rootfs 中都不存在**，`usbdevstart` 里的 `./usbd&` 是一条必然失败的命令。

## I.3 服务模式（`04DA:2370`）由 Linux 之外配置

`usbgadget` 脚本的默认值写死 `idProduct=0x2372`（PTP），服务模式需要 `0x2370`，
但**两个 rootfs 全文检索不到字符串 "2370"**（`grep -r 2370` 零命中）。
加上附录 H 的"请求帧从不进 Linux 内存"，可确定：服务模式的 gadget 与协议栈
由**协处理器侧**配置与实现，Linux 只提供 USB 控制器硬件。

## I.4 高段 DRAM 普查：全是图像缓冲，没有固件

- 结构侦察 `0x83100000–0x90000000`（16 MiB 步长）：处处高熵结构化数据。
- 活内存差分（每 1 MiB 采 8 KiB，两遍间隔 4 s）：变化点呈**严格周期**
  `0x90e00000 + k×0x1800000`（k=0…6），另有个别点（`0x84800000` 连两次相邻读
  都不相同，是正在被 DMA 写的缓冲）。
- 周期点并非地址镜像（8 个点内容互不相同，同一地址连读两次结果稳定）。
- 字符串密度普查（`0x83100000–0xA0000000`，1 MiB 步长）：标为"代码/文本区"的
  点内容实际是**渐变色阶**（`!"#$&'()+++,,.013689;=>ENTWW]hpz` 这类单调上升字节串），
  即测试图样/帧缓冲。
- 自指扫描在活区 `0x84800000–0x84c00000`（4096 块）**零命中**。

**结论**：可读窗口内的高段 DRAM 全部被图像/视频管线占用，不存在协处理器的代码或
固件；协处理器的 RAM 不在 31 位地址空间内。

## I.5 `0xC0000000` 窗口：不是协处理器内存

该窗口有稳定数据（`0x40000000` 为全零，两者不等），但内容是 0x40 字节步长的
图像类结构（熵 6.49，字符串全是噪声），且 `0x41000000`（预链接模块基址）读出全零。
无法据此认定其为第二执行环境的内存，**不构成可用通道**。

## I.6 签名机制：ECDSA 标准曲线被排除（纯离线，可复现）

新工具 `ecdsa_recover.py`（纯 Python 实现 P-256 / secp256k1 / brainpoolP256r1
的 Jacobian 点运算、Shamir 双标量乘、公钥恢复；`selftest` 用已知私钥造签名并成功
解回原公钥、错误哈希必给出不同公钥）。

方法：给定 `(r,s)` 与消息哈希 `e`，反解 `Q = r⁻¹(sR − eG)`。单次必得一个"公钥"，
但只有"消息区/哈希/曲线/字节序"全猜对时，两份不同容器才会解出**同一个 Q**
（误判概率 2⁻²⁵⁶）。

实测范围：

| 维度 | 取值 |
|---|---|
| 容器 | V2.8、V2.9（同机型 MC801）交叉；V3.7（S5M2）另计 |
| 消息区 | 15 种（整文件、`0x200..`、`0x2ec..`、`0x1600..`、目录表、去签名区、头副本…） |
| 哈希 | SHA-256 / SHA-1 / SHA-384 / SHA-512 / MD5 |
| 曲线 | P-256 / secp256k1 / brainpoolP256r1 |
| 布局 | `r‖s` 与 `s‖r` |

结果：三容器交叉 **0 命中**；同机型两容器交叉 **0 命中**；"blob 两半是否为某候选区
裸哈希"亦 **0 命中**。

**结论**：`0x220` 起的 64 字节**不是**标准曲线 ECDSA 签名，也**不是**候选区的裸哈希。
剩下的可能只有"非标准/私有曲线"或"对称 MAC（密钥在设备内）"。两者都无法离线判定，
且都要求设备侧持有秘密——与本项目"密钥只能从运行时取得"的总判断一致。

## I.7 明文组件全部是擦除态占位

目录中 `fl=0x2`（不加密）的 7 项：`storage`(0)、`history`、`lens_hist`、`fileinfo`、
`ninsho_db`、`wifi_info`、`menu_save`。其中 `fileinfo`(896 KiB) 与 `menu_save`(128 KiB)
的目录哈希不等于全零哈希，一度以为含内容；实测**全部字节为 `0xFF`**（闪存擦除态，
熵 0.000）。故没有任何可直接取用的明文资产。

# 附录 J：PTP 通道（`04DA:2382`）实测——不可达

本轮尝试了"不经 SD 卡、仅用一条 PTP 私有命令让 psm 进入固件更新模式"的思路。
**结论：本机 Windows 环境下 PTP 通道不可达**，原因不在我们的代码，而在设备未注册进
WPD 设备枚举器。

## J.1 设备形态

相机切到普通连接模式后以 `04DA:2382` 出现，描述符为**标准 PTP**：

| 字段 | 值 |
|---|---|
| InterfaceClass / SubClass / Protocol | `0x06` Image / `0x01` / `0x01` |
| 端点 | `0x01` Bulk OUT、`0x82` Bulk IN、`0x83` Interrupt IN（64 B, 8 ms） |
| 配置数 | 2（总线供电 500 mA / 自供电） |
| PnP Class | `WPD`，驱动 `WUDFWpdMtpX`（`wpdmtp.inf`），ProblemCode `0` |
| 实例 ID | `USB\VID_04DA&PID_2382\0000000000000000000XJR2208230009` |

## J.2 三条通路全部失败

1. **libusb 直连**：`set_configuration` → `Entity not found`；
   `claim_interface` → `Access denied`。WUDF/WPD 驱动独占接口，libusb 无法接管。
   （`ptp_probe.py` 已实现完整 PTP 事务层，驱动一旦可用即可直接跑。）
2. **WPD 枚举**：`IPortableDeviceManager::GetDevices` 与 `GetPrivateDevices`
   均返回 **0 个设备**。`WPDBusEnum` 服务原为 `Stopped`，启动后仍为 0；
   停止 `stisvc`（WIA）后仍为 0。
3. **WPD 直接 Open**：从注册表
   `HKLM\SYSTEM\CurrentControlSet\Control\DeviceClasses\{6AC27878-A6FA-4155-BA85-F98F491D4F33}`
   取到接口路径后调用 `IPortableDevice::Open`，返回 `E_ACCESSDENIED`。
   用 `GetDeviceFriendlyName` 验证该路径，返回 `E_ELEMENT_NOT_FOUND`
   ⇒ **该接口路径不是有效的 WPD device ID，设备并未注册进 WPD 设备存储**。

## J.3 判定

`04DA:2382` 虽然由 `wpdmtp.inf` 绑定、PnP 状态正常，但 **WPD 设备初始化未完成**
（libusb 侧读设备字符串同样失败，提示该模式下控制传输响应不完整）。
因此 `WPD_COMMAND_MTP_EXT_GET_SUPPORTED_VENDOR_OPCODES`
（`WPD_CATEGORY_MTP_EXT_VENDOR_OPERATIONS`, pid 11）取不到厂商操作码表，
`PsmCmd_Camctrl_fw_update_mode` 无从触发。

即便后续用 Zadig 把该 PID 换成 WinUSB 驱动（可逆，但会使 Windows 不再把相机识别
为相机），仍存在前置未知：**该私有命令的操作码与参数含义均未确定**，
盲发私有操作码在固件更新语境下的风险不可控。故不再沿此路推进。

## J.4 副产品

| 工具 | 作用 |
|---|---|
| `ptp_probe.py` | 完整 PTP 客户端（OpenSession / GetDeviceInfo / 事件监听 / 任意操作码），驱动可用即可直接用 |
| `wpd_mtp.py` | 经 WPD 的 MTP 扩展命令通道（含 `GET_SUPPORTED_VENDOR_OPCODES`），当前因 J.2 不可用 |

同时确认：WPD 的 MTP 扩展机制本身可用（`comtypes` 可从 `PortableDeviceApi.dll`
类型库生成全部接口），瓶颈只在设备注册这一环。

# 附录 K — 镜身固件 `.plf` 容器格式（已完全解析，无签名）

分析对象：`E:/desktop/LUMIX/400BV020.plf`（361 176 字节，S 20-60 / S-R2060 镜身固件）。

## K.1 总体结构

```
0x00000  "LENS-UPDATE-FILE-SOF:"        21B   ASCII 魔数
0x00015  SOF 元数据                      67B
0x00058  "LENS-UPDATE-FILE-EOH:"        21B   ASCII 魔数
0x0006D  "PSLF"                          4B   段魔数
0x00071  EOH 元数据                      51B
0x000A4  块链 586 个块                   ...
0x48204  第二段（型号相关参数区）      65 748B   到 EOF
```

字节归属核算**完全闭合**：`164 + (586×16 + 285 888) + 65 748 = 361 176`，与文件长度
**差 0 字节**。也就是说，**文件里没有任何隐藏的签名块、证书块或预留区**。

## K.2 块格式与校验算法

```
"@@@@"(4) | addr(BE32) | len(BE32) | payload(len) | ck(BE32)

ck = (addr + len + Σ32be(payload)) mod 2^32
```

`Σ32be` = 按 4 字节大端字求和（尾部不足 4 字节补零）。

验证结果：**586 / 586 个块全部命中**。这是纯加法校验和，不是 CRC、不是 HMAC、
不是签名。

对照：机身 `.bin` 更新包的 CRC32 只覆盖 `0x200..EOF`，签名区在 `0x220` 起 64 字节；
而镜头 `.plf` **完全没有对应结构**。

## K.4 映像布局（按 addr 重组成连续映像后）

| 地址范围 | 大小 | 内容 |
|---|---|---|
| `0x00000–0x1FFFF` | 128 KiB | **引导区，不在 `.plf` 内**，`.plf` 解析器就在这里 |
| `0x10000–0x20000` | 64 KiB | 标定/参数数据，起始为 `CABRIOLET\x00\x01A` |
| `0x20000` | — | **向量表**：SP=`0x20008114`，复位向量=`0x00000401` |
| `0x20000–0x60000` | 256 KiB | 应用代码（Cortex-M Thumb，明文未压缩） |
| `0xFFFF0` | 16 B | 唯一内容：`00 11 22 33 44 55 66 77 88 99 AA BB CC DD EE FF` |

- 覆盖密度 285 888 / 983 040 = **29.1%**（稀疏块，只写变更区）
- 地址跨度 `0x10000–0x100000`，与头部 EOH 元数据里的字段 `0x000F0000` 一致
- `0x20300` 是二级引导桩：`bl 0x53C18` → 设 SP → `bx 0x000569FD`（应用入口 `0x569FC`）

CPU 为 **Cortex-M**（Thumb-2，含 `push.w {r0-r8,sl,fp,lr}` 等 32 位宽指令），
RAM 基址 `0x20000000`。

## K.5 字符串取证

| 偏移 | 内容 | 归属 |
|---|---|---|
| `0x4822E` | `LUMIX S 20-60/F3.5-5.6`（空格补足 48B） | 尾段，型号串 |
| `0x48337` | `Panasonic` | 尾段 |
| `0x43496` / `0x45FAE` | `Vario-Elmar T 1:3.5-5.6 / 18-56 ASPH.` | 代码区，**徕卡**同底板型号表（两份） |
| `0x000B0` / `0x582C4` | `CABRIOLET` | 项目代号，作为起止标记 |

结论：**代码区是跨型号通用底板，尾段才是型号相关参数**，型号串指的是尾段那一份。

全映像**没有** `LENS-UPDATE-FILE` / `PSLF` / 更新流程相关字符串，印证 K.4 第一条：
`.plf` 的解析与写入在引导区（不可更新区）完成。

## K.6 结论与风险

1. **`.plf` 无签名、无 MAC、不加密。** 校验和可自由重算 ⇒ 可以任意改固件，
   且改出来的文件在格式上完全合法。
2. 已知的改动入口：
   - 尾段 `0x4822E` 型号串（改完机身在 EXIF 里直接可见，是最便宜的"生效证明"）
   - 任一代码块（改完由 `plf_repack.py patch` 自动重算该块校验和）
3. **未知项只剩一个**：引导区里是否存在"新版本号必须大于当前版本"的门。
   这一条无法从 `.plf` 内部得出（门在引导区，不在升级范围内），只能实测。
4. **不可逆风险**：写坏应用区后，若镜头不再正常应答，机身的"镜头固件更新"菜单
   可能不再提供入口，届时只能靠引导区（若有恢复入口）或返厂。

## K.8 与机身侧的关系

机身 Linux (`rootfs1`/`rootfs2`) 与 49 MiB 内存 dump 中，`LENS-UPDATE-FILE`、
`PSLF`、`.plf` **零命中**。这说明机身不解析该文件，最可能是把 SD 卡上的
`.plf` 原样经卡口通道流给镜头，由镜头自身引导区完成校验与烧写。

若成立，则**唯一的校验者就是镜头引导区**，而它手里没有可用的签名（K.1 已证明文件里
没有任何签名字段）。
