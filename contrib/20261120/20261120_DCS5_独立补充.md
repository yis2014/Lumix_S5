# DC-S5 独立补充：rootfs 完整提取、容器校验补充、AES 表位置（2026-11-20）

来源：另一条独立会话，同一机型（DC-S5，官方 V2.9）。
采集方式与交接文档一致：Service USB（`04DA:2370`）只读 `0x5C` 读内存；
未在本仓库覆盖的范围内做任何写入。文中每条都标注了证据强度。

## A. [已证实] Linux rootfs 完整提取（配合 `dumps/rootfs1_dump.bin`、`rootfs2_dump.bin`）

两个 rootfs 由内核命令行 `slram` 设备提供：

```
root=/dev/mtdblock0 slram=slram0,0x83100000,+0x00300000,slram1,0x83400000,+0x00A00000 console=ttyAMA,115200
```

对应关系与镜像参数：

| 区域 | 地址 | bytes_used | inode 数 |
|---|---|---|---|
| rootfs1 | `0x83100000` | `0x26C153` (2,539,859) | 555 |
| rootfs2 | `0x83400000` | `0x95F1B4` (9,826,740) | 437 |

### 提取要点（对 `rootfs*_dump.bin` 直接可用）

1. **inode / directory 表的元数据块全部未压缩**（块头 bit15 = 1，`0xA000` 之类），
   所以不需要 LZO 解压器就能解析 inode 与目录项。
2. **目录表**：2 个未压缩块 + 1 个很小的 LZO 压缩尾块（rootfs1: 161→288 字节；
   rootfs2: 426→800 字节），用 `lzo1x_decompress`（动态长度）即可。
3. **fragment 表位置**：`fragment_table_start` 存的不是条目本身，而是一个 u64
   查找指针；**fragment 条目块就是该 u64 指向的块**，目录表止于此块。
   这是之前小文件全部解压失败（`unexpected end of input`）的原因。
4. 文件数据块压缩时按 128 KiB 解压，尾部块用动态长度。

### 结果

- rootfs1：**171 个文件 / 67 个目录**，零错误
- rootfs2：**384 个文件 / 53 个目录**，零错误
- 完整文件树：`contrib/20261120/trees/rootfs1_tree.txt`、`rootfs2_tree.txt`

Linux 侧完全没有 SD 卡自动执行逻辑：`rcS` 只执行
`S02-mount / S03-modules / S10-ifup / S20urandom`；`/etc/fstab` 只有 tmpfs/devpts；
`/usr/pvc/bin` 全是 WiFi/BT/DLNA/PTP 工具。相机 UI、SD 与固件更新仍归主核。

## B. [补充] 更新容器的两处校验细节（`analysis/partitions.json` 已覆盖字段，这里只补差异）

`partitions.json` 已经给出了每条记录的 `offset`（镜像偏移）、`size`、
`target_or_logical_offset`（flash 地址）、`flags` 和 `aux16`（IV）。
以下三点是目前 `analysis/` 里没有的：

### B1. 外层 CRC32

`S5___V29.bin` 的 `0x40..0x43` 是 **CRC32，覆盖 `file[0x200:]`**（小端）：

```python
struct.pack_into('<I', buf, 0x40, zlib.crc32(buf[0x200:]) & 0xffffffff)
```

官方文件该值为 `0x8E73AAC0`。修改目录或数据后必须重算，否则更新器在
菜单阶段就会拒绝（表现为“固件更新”不可选）。

### B2. 版本门在容器头 `0x1C`

`0x1C` 处是两个小端 u16，V2.9 为 `0x0290`（BCD 2.90）：

- 改成 `0x0291`、其余字节不动 → 相机接受并显示 `Ver 2.9`，可正常更新
- 更新完成后机身**仍报 2.9** → 该字段只是“是否允许开始”的门，不是版本存储

这与交接文档中 `0x863B0000`/`0x863181E2` 的 **RAM 版本伪装是两套独立机制**，
可以叠用，也可以单独用容器头方式做同版本重刷。

### B3. `flags == 2` 的实证

7 条 `flags == 2` 的记录（`storage`、`history`、`lens_hist`、`fileinfo`、
`ninsho_db`、`wifi_info`、`menu_save`）满足
`SHA-256(数据区 blob) == 记录里的 32 字节摘要`，7/7 命中。
`flags == 3` 的记录长度与明文一致，10 MB 分区内没有任何重复 16 字节块（非 ECB）。

数据区布局：`文件偏移 = 0x200 + img_off`，各 blob 按记录顺序首尾相接，
`Σsize = 0x560D800`，`0x200 + Σsize = 0x560EE00`（文件尾）。

附件：`contrib/20261120/section-map.txt`（48 条记录全字段）。

## C. [存疑] root 空密码 + 串口 getty

从本会话提取的 rootfs1 中读到：

```
/etc/shadow : root::10933:0:99999:7:::
/etc/inittab: AMA0::respawn:/sbin/getty -L ttyAMA -s vt100 # GENERIC_SERIAL
```

**文件内容已核实**（来自 `0x83100000` 的 squashfs 明文）。
**推论未验证**：若主板 UART 可接出，115200 8N1 应直接得到免密 root shell。

之所以标为存疑：
- 未做任何硬件连接，未确认 ttyAMA 对应的物理引脚；
- 未确认业务固件是否会改写 shadow / 关闭 getty。

如果这条成立，它提供的是 Linux 侧 shell，不涉及主核 Flash，也与验签无关。

## D. [数据] AES 表位置与密钥扫描负结果

RAM（`0x80000000..0x83000000`，48 MB）中完整 AES S-box 出现 5 次，
均伴随逆 S-box（多数相隔 `0x100`）：

```
0x80FCB5E0 / 0x80FCB6E0
0x8171984A / 0x8171994A
0x817435E0 / 0x817436E0
0x81BB112E
0x81BCAF00
```

其中前两处前面紧邻编译路径字符串
`C/MC561_2ND/bluetooth-1.0/blueangel/btcore/btutils/src/rxbuff.c`，
说明这些表至少有一部分属于蓝牙栈，不能假定就是机身更新密钥所在模块。

扫描结果（负）：以 `eep_ow_a` / `eep_ow_b`（明文相同、IV 不同）为首块判据，
在上述 5 处各 ±128 KiB、4 字节对齐范围内共检查 **303,451 个候选 16 字节密钥**，
**无命中**；也未用 `loader1` 的 SHA-256 验证出任何可通过的密钥。

这不否定“密钥运行期存在”的结论，只说明它不在活动 RAM 的这几个 AES 表附近。
